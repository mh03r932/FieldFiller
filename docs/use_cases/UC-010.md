# Use Case: Edit a Custom Field Rule

## Overview

**Use Case ID:** UC-010
**Use Case Name:** Edit a Custom Field Rule
**Primary Actor:** Power User
**Goal:** Change an existing rule as the application it was written for changes
**Status:** Draft

Includes UC-013 (preview) and UC-024 (persist).

**Traces to:** FR-040, FR-070

## Preconditions

- At least one rule exists
- The Power User has the options page open

## Main Success Scenario

1. The Power User opens a rule from the list.
2. The system expands it in place, showing its current values and its samples (UC-013).
3. The Power User changes any part of it.
4. The system validates and, if valid, writes the whole rule list (UC-024, BR-009-1).
5. The change applies to the next fill in every tab.

## Alternative Flows

### A1: The change makes the rule invalid

**Trigger:** Any edit that fails validation (step 4)
**Flow:**

1. The problem is shown beside the field that caused it.
2. **The previously stored version of the rule stands**, unchanged, and keeps being used by
   fills until the edit becomes valid.
3. Nothing is written.

**Stated because the alternative is tempting:** disabling or deleting the rule while it is
mid-edit would mean a fill behaving differently because somebody was typing.

### A2: The rule is edited while a fill is running

**Trigger:** A fill is in progress in some tab (step 4)
**Flow:**

1. The running fill continues with the settings it was issued with (BR-024-6).
2. The next fill uses the new rule.

**Why the running fill is not interrupted:** it carries its own settings, so there is nothing
to interrupt. A fill that changed rules halfway through would produce a form filled by two
different configurations, which is not something the report could explain.

### A3: The Power User disables rather than edits

**Trigger:** The rule is toggled off (step 3)
**Flow:**

1. The rule is kept in the list, in its position, with everything it had.
2. It is skipped when a fill selects rules (FR-031).
3. The system writes the change immediately, as with any other edit.

**Why disabling exists at all:** it is how a user tests whether a rule is the one causing an
unexpected value, without losing the rule while they find out.

## Postconditions

### Success Postconditions

- Storage holds the edited rule, in its original position
- Every other rule is untouched, including its order
- The rule's samples on screen reflect what was stored

### Failure Postconditions

- Storage holds the rule as it was before the edit
- The problem is stated beside the field that caused it

## Business Rules

### BR-010-1: Editing never changes order

An edit changes what a rule does, never when it is consulted. Reordering is UC-012 and is a
separate, deliberate action — because first-match-wins means a position change alters the
behaviour of rules the user was not editing.

### BR-010-2: The rule's identity survives editing, and is the rule's alone

A rule keeps its identity across every edit, including a change of generator type. That
identity is what a future profile, export or report refers to; regenerating it on edit would
turn every edit into a delete and a create.

It must also be *unique within its list*, which was assumed rather than stated until 2026-08-24.
The editor mints an identity per rule and never repeats one, so the assumption held for every
rule this extension wrote. It did not hold for a rule read out of a file that states none: the
identity fell back to the match pattern, so two rules matching `email` shared one, and every
editor write is keyed on it — editing one relabelled both, deleting one deleted both. Fills were
never affected, because matching walks the list in order and takes the first hit, which is why
the defect was invisible from the outside. The fallback now qualifies the pattern with the
entry's position. A file that *repeats* an explicit identity still collides, and nothing reports
it today: that is a file stating two entries are the same rule, a parser that renamed one would
be overruling the file rather than reading it, and naming the contradiction belongs to the import
preview (UC-026 step 5) where it is **owed and unbuilt**.
