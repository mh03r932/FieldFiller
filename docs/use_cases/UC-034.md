# Use Case: Fill Fields That Depend on an Earlier Answer

## Overview

**Use Case ID:** UC-034
**Use Case Name:** Fill Fields That Depend on an Earlier Answer
**Primary Actor:** *(none — included subfunction of UC-001, UC-002, UC-003)*
**Goal:** Follow the page's own reaction to being filled — options rewritten, fields revealed,
controls enabled, values reverted — until the page settles or a declared bound is reached
**Status:** Draft

Included by UC-001, UC-002 and UC-003. Includes UC-004 and UC-005, which it re-enters once per
pass. Runs in the page agent, in each frame independently.

**Traces to:** FR-076, FR-077, FR-078, FR-079, FR-081 · **Design:** DD-009

A single-pass fill assumes the page is finished changing by the time it is walked. Choosing a
country rewrites the state list; ticking a box reveals three fields; picking a plan enables a
seat count. This use case is what makes the walk a conversation rather than a snapshot.

> The combobox ladder (A9, A10, FR-081) is specified here for completeness but is gated on a
> measurement and may not ship: per `vision.md` §3, reaching further is coverage rather than
> correctness, and it is the part of DD-009 that yields to NFR-003. A combobox reported as
> skipped with its reason satisfies this use case.

## Preconditions

- A fill operation is in progress in this frame, and its first pass has applied values
- The persona for the operation exists and is unchanged for its lifetime (BR-004-1a)
- The set of controls this frame has already written is known by element identity (BR-005-7)

## Main Success Scenario

1. The system verifies each value as it writes it, recording a control as filled only where
   the write was accepted by the control (A6).
2. The system begins watching the frame for structural change and for changes to the
   attributes that govern availability.
3. The system waits until the frame has stopped changing, or until the pass's maximum wait
   elapses, whichever comes first.
4. The system examines the frame for work the previous pass could not have done: controls that
   did not exist; controls whose available choices have been rewritten; controls excluded for a
   reason that no longer applies; and controls whose written value did not survive.
5. Where that set is empty, the system continues at step 8.
6. The system classifies (UC-005) and fills (UC-004) that set as a further pass, drawing from
   the same persona, and giving any control it has already filled the same value it gave it
   before.
7. The system repeats from step 2, until a pass finds no work or a bound is reached (A4).
8. The system checks, once more, that every value it wrote is still present, and takes the
   result of that check as each control's outcome.
9. The system reports exactly one outcome per control, together with the number of passes and
   whether it stopped because there was nothing left to do or because it reached a bound.

## Alternative Flows

### A1: The page rewrites a control's choices after it was filled

**Trigger:** A control's available options differ from those the system chose from (step 4)
**Flow:**

1. The system treats the control as unfilled, whatever it currently holds — a value chosen
   from a list that no longer exists is not a valid answer even when the control still
   displays it.
2. The system includes the control in the next pass.
3. The use case continues at step 6.

This is the case the use case exists for. A country select filled before its state list
arrives leaves the state select holding a placeholder, and the form fails validation on a
field that looks answered.

### A2: Controls appear, or become available, only after an earlier answer

**Trigger:** A control exists that the previous pass did not classify, or a control the
previous pass excluded is no longer disabled, read-only or hidden (step 4)
**Flow:**

1. The system classifies the control as though the fill had just begun (UC-005).
2. A control that is now fillable joins the next pass; one still excluded keeps its exclusion,
   with the reason re-evaluated rather than carried forward.
3. The use case continues at step 6.

A control's eligibility is re-decided, never remembered: the reason a control was excluded in
pass 1 is a statement about pass 1.

### A3: The page reverts a value the system wrote

**Trigger:** A control the system filled no longer holds what was written (step 4 or step 8)
**Flow:**

1. The system includes the control in the next pass, and writes it the value it wrote before
   (BR-034-3).
2. Where a bound is reached before the value survives, the control's outcome is failed, and
   the cause names the page as having discarded the value — never filled.

### A4: The page and the system cannot agree

**Trigger:** Passes continue to find work until the pass cap, the per-pass wait or the total
cascade budget is exhausted (step 7)
**Flow:**

1. The system stops, writing nothing further.
2. The system takes each control's outcome from the state it is actually in, not from the last
   write attempted.
3. The system reports the fill as capped, naming how many controls may be stale.
4. The use case ends — successfully, in the sense that it produced a true account of a page it
   could not settle (BR-034-6).

This covers a validation bug that reverts a select on every change, two controls that rewrite
each other, and a handler that throws on the interaction the system dispatches. None of them
has a fixpoint, and none of them is distinguishable from a slow cascade until the bound is
reached.

### A5: The Tester interacts with the page during the fill

**Trigger:** An input, key press or pointer interaction originating from the Tester rather than
from the system reaches the page while the fill is in progress (any step)
**Flow:**

1. The system writes nothing further to the control the Tester touched, for the remainder of
   the operation.
2. The system abandons the remaining passes.
3. The system reports what it had completed, marked as capped, so the shortened fill is not
   read as a settled one.

The system's own writes and the click it gives a checkbox are not Tester interaction and must
never trigger this flow.

### A6: A control rejects the value written to it

**Trigger:** After a write, the control does not hold a value its kind would accept (step 1) —
an empty date field given an unparseable date, a control whose handler threw
**Flow:**

1. The system records the control as failed, with the cause.
2. The system does not retry it in a later pass on that basis alone; a rejected value is a
   generation problem, not a staleness problem.
3. The use case continues at step 2.

A value the page reformatted, normalised or truncated has been accepted, not rejected
(BR-034-4).

### A7: A control is replaced rather than updated

**Trigger:** The page removes a control and inserts another in its place — a re-render that
swaps the element (step 4)
**Flow:**

1. The system treats the replacement as a control it has not seen, because it has not.
2. The replacement is filled with the same value as the control it replaced, where it resolves
   to the same persona attribute (BR-034-3).
3. Both appear in the report. The count of controls may therefore exceed the number of
   controls visible on the settled page.

Correcting the count would mean inferring that two elements are "the same field", which is a
guess. An honest over-count is preferred to a confident wrong identity.

### A8: The frame never stops changing

**Trigger:** Structural change continues throughout the pass's maximum wait — an animation, a
carousel, a polling widget (step 3)
**Flow:**

1. The system proceeds without waiting for quiet.
2. The system examines the frame as it would have at quiescence.
3. The use case continues at step 4.

Change unrelated to the fill must not be able to extend it indefinitely, and cannot be
distinguished from change caused by the fill without knowing more about the page than the
system does.

### A9: A control is a custom combobox

**Trigger:** A control declares itself a combobox or listbox rather than being a native select
(step 6)
**Flow:**

1. The system records where focus and scroll are before touching it.
2. The system opens the control with the keyboard, reads the choices the control then offers,
   selects one with the keyboard, and confirms.
3. Where that does not take, the system clicks the control open, reads the choices, and clicks
   one.
4. The system verifies the control's own displayed answer, not any hidden field behind it.
5. The use case continues at step 1 for the next control.

### A10: A custom combobox cannot be driven

**Trigger:** Neither interaction in A9 produces a verified answer
**Flow:**

1. The system closes the control and restores focus and scroll to where they were.
2. The system records the control as skipped, with a reason naming it as a control it could not
   drive.
3. The use case continues at step 1 for the next control.

A page left holding an open popup, a focus trap or a scroll lock because the system walked away
mid-interaction is a worse outcome than an unfilled field.

### A11: The frame is destroyed mid-cascade

**Trigger:** The frame navigates, is removed, or the page unloads (any step)
**Flow:**

1. The system stops. Values already written remain; nothing is rolled back.
2. No report is produced from this frame, and the operation's own deadline closes it
   (BR-001-5).

### A12: The value source cannot be reached for a later pass

**Trigger:** A pass cannot obtain values — the background context was evicted and restarted, or
the extension is mid-update (step 6)
**Flow:**

1. The system records every control in that pass as failed, with the cause.
2. The system attempts no further passes.
3. The use case continues at step 8, so the report still accounts for every control.

## Postconditions

### Success Postconditions

- Every control the operation touched carries exactly one outcome, taken from the state the
  control was actually in when the fill ended
- Every control filled from a list of choices was filled from the list the page was offering
  when the fill ended, not from an earlier one
- The result states how many passes ran, and whether the fill settled or was capped
- No control the Tester interacted with during the fill was written after they touched it
- Nothing the system installed to observe the page is still installed
- No value read from a control has been retained, transmitted, or included in the report

### Failure Postconditions

- Values written before the failure remain; nothing is rolled back
- Controls with no outcome do not exist: a control whose fate is unknown is reported as failed,
  never omitted and never assumed filled
- The page is left with no popup open, no focus trap, and no scroll position the system moved
  and did not restore
- The frame's report, or the operation's deadline, closes the operation — a cascade cannot
  leave a fill open indefinitely

## Business Rules

### BR-034-1: A fill ends when the page stops changing, not when a timer expires

Completion is decided by the page going quiet, bounded by a cap. A fixed delay is wrong in both
directions at once: too short for a cascade behind a debounce or a page-side request, and paid
on every ordinary fill that never needed it.

### BR-034-2: One outcome per control, decided last

A control filled in one pass, reverted by the page, and refilled in another has one outcome,
not three. The outcome is taken at the end, because only then is it known whether the value
survived — and a fill that reports what it *attempted* rather than what *holds* is the silent
failure this whole use case exists to remove.

### BR-034-3: A control's value does not change within one fill

Where a control must be written more than once during a single fill, it receives the same value
each time. Otherwise a field and its confirmation drift apart whenever the page forces a second
write (FR-024, FR-080), and the defect appears only on pages that cascade — the hardest place to
notice it.

This is scoped to one fill. Filling the same page again still produces a new person
(BR-001-3, FR-075).

### BR-034-4: Verification asks what the control kind can accept

A written value is verified against what the control could reasonably hold, never by exact
string comparison. A number field given `007` holds `7`; a colour field normalises case; a
length-limited field truncates; a mask turns `1234` into a formatted amount. All of those were
accepted. Only an empty control, or one whose contents its own kind rejects, has failed.

Exactness applies where exactness is available: a checkbox is in the state it was set to, and a
select holds the option that was chosen.

### BR-034-5: The Tester outranks the fill

A cascade can stretch a fill from milliseconds to seconds, which is long enough for the Tester
to start typing into it. Nothing the system writes may land on a control they have touched since
the fill began, and their first real interaction ends the cascade.

This is the only failure in this use case where the Tester loses work rather than the fill being
incomplete, which is why it is a rule and not a mitigation. Interaction the system itself
produces is not Tester interaction and must be distinguishable from it by construction, not by
timing.

### BR-034-6: Stopping at a bound is a result, not a truncation

A fill that cannot settle stops, and says that it stopped. It is reported as a distinct outcome
from a fill that finished — never folded into the count, never presented as clean. Per
`vision.md` §3 a bounded honest failure is the correct behaviour; running unbounded in pursuit
of completeness is not more correct, only unfinished.

### BR-034-7: A further pass is earned, not automatic

A later pass covers only controls with a reason to be revisited: newly present, newly eligible,
choices rewritten, or value not survived. A control that still holds what the system wrote is
left alone; so is one the page cascaded to a sensible default of its own.

A control skipped for this reason keeps the outcome it already earned. It must never be reported
as pre-filled, which would be a lie about why it was left alone, and one the result would then
repeat to the user.

### BR-034-8: What the page did is established by looking, not by being told

Change notifications decide *when* to look; the state of the frame decides *what* changed. The
two cannot be collapsed. A framework reverting a value does so in a way that produces no
notification at all, so a system that trusts notifications alone is blind to precisely the case
it most needs to catch — and would then report those controls as filled.

### BR-034-9: A custom control is driven the way a user drives it, or not at all

Custom comboboxes are operated through the keyboard and pointer interactions their design
intends, and the answer is verified through what the control displays. Writing to a hidden field
behind such a control is never acceptable: it updates what the form submits without updating
what the component believes, producing a page reading "Select…" and a submission carrying a
value — wrong, and invisible.

### BR-034-10: The page is left as it was found, apart from the values

Anything the system opens, it closes. Focus and scroll are returned to where they were. Nothing
installed to watch the page outlives the fill (NFR-035). The extension is present on every page
the Tester visits (DD-001), so a fill that leaves something behind leaves it behind everywhere.

### BR-034-11: Reading a control back retains nothing

Verifying a write means reading the control, which is page-originated data. The comparison
happens within the fill that made the write and goes no further: no value read back is stored,
sent, or placed in the result. NFR-010 and NFR-030 hold without exception.
