# Use Case: Create a URL Profile

## Overview

**Use Case ID:** UC-014
**Use Case Name:** Create a URL Profile
**Primary Actor:** Power User
**Goal:** Scope a named rule set to the pages it belongs to
**Status:** Draft

Includes UC-024 (persist and propagate). Its rules are authored by UC-009..UC-013 unchanged;
they are applied by UC-007 and reported by UC-017.

**Traces to:** FR-045

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows the profiles that exist, in the order they are consulted, and states that
   the first one whose address pattern matches a page is the one that governs it.
2. The Power User adds a profile. It appears at the end of the list, opened for editing, named
   nothing and matching nothing.
3. The system states that the profile matches no page until it is given an address pattern.
4. The Power User gives it a name and one or more address patterns.
5. The system stores each change as it is made (UC-024) and stops stating the problem once the
   profile matches something.
6. The Power User writes rules inside the profile, using the rule editor (UC-009..UC-013).
7. On a page the profile matches, its rules are tried before the global ones (UC-007), and the
   fill report names the profile (UC-017).

## Alternative Flows

### A1: Another profile already matches those pages

**Trigger:** A new profile's patterns overlap an existing profile's (step 4)
**Flow:**

1. The profile earlier in the list governs the page. The new one, being appended, does not.
2. The Power User moves it above the other to change that.
3. Nothing warns about the overlap: two profiles matching one page is a normal configuration,
   and the list order says which wins.

### A2: The profile has no address patterns

**Trigger:** A profile is created, or its last pattern is removed (steps 2, 4)
**Flow:**

1. The profile matches no page and its rules never run.
2. The system marks the profile in the list and states the problem inside it.
3. The profile is stored anyway. It is a profile being written, not an invalid one.

### A3: An address pattern is not usable

**Trigger:** A pattern is empty or contains whitespace (step 4)
**Flow:**

1. The system states the problem beside the field, using the same validation the site
   exclusions use.
2. The pattern is stored, and it matches nothing until it is fixed.

### A4: The change cannot be stored

**Trigger:** Storage rejects the change (step 5) — see UC-024 A2
**Flow:**

1. The previous set of profiles remains in force.
2. The system reports that the change did not take effect, and why.

## Postconditions

### Success Postconditions

- The profile exists, in the position the Power User left it
- Its rules run ahead of the global rules on every page it matches, and nowhere else
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous set of profiles remains in force
- No profile exists in a half-written state that a fill could act on

## Business Rules

### BR-014-1: A new profile matches nothing, and says so

Not everything. Both are readings of an empty pattern list, and the difference is a
half-written profile governing every tab the user opens — silently, from the moment they click
Add, before they have said which application it is for.

Matching nothing is also the reading whose failure is *visible*: the profile is marked in the
list and the problem is stated inside it, so an inert profile cannot be mistaken for a working
one. It is the same choice UC-009 A6 makes for a rule scoped to no source.

### BR-014-2: Order is precedence, and it is the only tiebreak

The first enabled profile whose patterns match the page governs it. No specificity rule, no
longest-match, no scoring.

A user cannot predict a specificity rule without being taught it, and a matcher the user cannot
predict is the defect ND-2 names. A list they can read top to bottom and reorder is
predictable by inspection — and reordering is a keyboard-operable button, not a drag, for the
reason UC-012 gives.

### BR-014-3: One profile governs a page, not all that match

Concatenating every matching profile's rules would make the outcome depend on how many
profiles happened to overlap, which is exactly the unpredictability FR-031 removes for rules.
UC-017 also has to be able to *name* the profile that applied, which presumes there is one.

### BR-014-4: A profile adds to the global rules, it does not replace them

Its rules are tried first; the global list still follows. A profile is a set of exceptions for
one application, not a mode.

Replacing would mean every profile had to restate the user's general rules, and forgetting one
would be invisible until a field came out wrong on that application alone — which is the
hardest kind of defect to attribute, because the same rule works everywhere else.

### BR-014-5: A profile's rules are the same rules

The same thirteen generators, the same three match modes, the same validation, the same
preview, the same per-rule source scoping, the same reordering. Nothing about authoring a rule
changes because it lives inside a profile.

This is a constraint on the implementation as much as on the specification: the editor is one
editor pointed at a different list. Two editors would be two sets of defects, and the first
divergence would be a profile rule that could be written but not validated the same way.

### BR-014-6: Address patterns use the same vocabulary as the site exclusions

`*` for any run of characters, everything else literal, port ignored — validated by the same
function, matched by the same non-backtracking matcher (BR-021-2).

One vocabulary, so a pattern cannot mean one thing in the exclusion list and another here. The
consequences of getting one wrong differ, though, and the difference is worth knowing: a
too-broad *exclusion* refuses a fill and marks the tab, while a too-broad *profile* silently
changes which rules ran.
