# Use Case: Configure Fill Behaviour Defaults

## Overview

**Use Case ID:** UC-022
**Use Case Name:** Configure Fill Behaviour Defaults
**Primary Actor:** Power User
**Goal:** Set what a fill does to the controls it has decided to fill
**Status:** Draft

Includes UC-024 (persist and propagate). Configures behaviour UC-004 and UC-006 apply.

**Traces to:** FR-014, FR-015, FR-024, FR-049, FR-065

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows whether the page is told about each value it receives, and what turning
   that off costs.
2. The system shows a default length limit per free-text control kind, each of which may be
   unset.
3. The system shows the words that mark a checkbox as a consent gate, and the words that mark a
   field as confirming an earlier one.
4. The Power User changes any of these.
5. The system stores the change (UC-024).
6. The next fill behaves accordingly, in every open page, without a reload.

## Alternative Flows

### A1: A length limit is cleared

**Trigger:** The box for a control kind is emptied (step 4)
**Flow:**

1. The kind has no configured limit, which is not the same as a limit of zero.
2. Controls of that kind receive the built-in sizing — a paragraph for a text area, a phrase
   for a text input.

### A2: A control declares its own limit

**Trigger:** A control carries `maxlength` (during a fill)
**Flow:**

1. The control's own limit is applied and the configured default is not consulted.
2. This use case has no part in it. A configured limit that overrode the page would produce
   values the page's own validation rejects.

### A3: The consent list is emptied

**Trigger:** The last consent keyword is removed (step 4)
**Flow:**

1. No checkbox is ticked *for being a consent gate*.
2. Required checkboxes are still ticked, which is a separate rule and is not configurable.
3. Every other checkbox is decided as it always was.

### A4: A keyword is a blank line

**Trigger:** The list is typed with an empty line among the words (step 4)
**Flow:**

1. The blank is dropped rather than stored.
2. Nothing is reported. A blank line is a typing artefact, not an instruction.

### A5: The change cannot be stored

**Trigger:** Storage rejects the change (step 5) — see UC-024 A2
**Flow:**

1. The previous behaviour remains in force.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

## Postconditions

### Success Postconditions

- The stored settings are what the Power User chose
- The next fill dispatches events, sizes values and recognises consent and confirmation fields
  accordingly
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous behaviour remains in force
- No fill has run under a half-applied configuration

## Business Rules

### BR-022-1: A blank keyword is dropped, twice

Once on the way out of the screen and again in the parser, because this page is not the only
writer the parser has to survive.

A keyword of `''` is a substring of every identity, so one stray blank line would tick every
checkbox on every page — and a blank line is the one edit that looks like nothing at all on
screen. An emptied *list* is a different thing and is kept: it means "tick nothing for
consent", which is a choice.

### BR-022-2: Keywords are literal, never patterns

Each is escaped before it is compiled. A user typing `c++` gets a keyword rather than a syntax
error or an accidental wildcard, and no configured word can introduce the backtracking NFR-009
keeps off this path.

### BR-022-3: Two rules beside these are not configurable, and the screen says so

**A required checkbox is always ticked.** An unticked required box blocks the submission the
fill exists to reach, so it is a property of the form rather than a preference.

**A trailing ordinal marks a confirmation.** `password2` beside `password` is a confirmation,
and that is a convention about shape rather than a word. It cannot be expressed in a list that
escapes its entries, and a screen offering "confirmation keywords" would otherwise be read as
offering all of it. The one exception stays in the engine too: `address2` is the *next* line,
not the same line said twice.

### BR-022-4: Length limits are offered only where truncation is not destructive

Text inputs, search inputs, text areas and rich text areas. Not email, telephone or URL: a
truncated address is not a shorter address, it is a broken one, so offering a limit there would
be offering a way to make fills fail.

The kind this setting exists for is the text area. ND-10's papercut is the reference giving an
unconstrained text area twenty characters, from a single global default; this is where a user
says what it should get instead, per kind.

### BR-022-5: The page always wins on length

A configured limit applies only where the control declares no `maxlength` of its own. Same
argument as BR-019-3, for a different value: ND-11 arriving through the settings screen is
still ND-11.

### BR-022-6: Turning off event dispatch is offered with its cost stated

React, Vue and Angular forms need the events to notice the value at all, so a user who turns
this off to fix one misbehaving page can silently break every framework-driven form they test
afterwards. The screen names the cost rather than leaving it to be discovered.

### BR-022-7: The behaviour a fill runs under is fixed when it begins

Settings are read once per operation, so every frame of every pass is generated against one
configuration. Reading them per batch would let a fill that spans a settings change tick a
consent box in one frame and not in the next, which is the incoherence ND-1 exists to prevent
wearing a different hat.

## Notes

FR-049 names "default maximum length, consent keywords and confirmation keywords" and all three
are here. The keyword lists did not exist in the schema before this use case: DD-005 fixed the
whole shape in Phase 2, and these were the one addition Phase 4 had to make to it. They are
additive keys within an existing section, which the tolerant parser handles by defaulting —
unlike a restructuring, which FR-073 records as the change that would force the migration
ladder to be built.
