# Use Case: Reorder Custom Field Rules

## Overview

**Use Case ID:** UC-012
**Use Case Name:** Reorder Custom Field Rules
**Primary Actor:** Power User
**Goal:** Control which rule wins when more than one matches the same field
**Status:** Draft

Includes UC-024 (persist).

**Traces to:** FR-031, FR-042, NFR-019

Order is not presentation. The first matching rule wins and evaluation stops (FR-031), so the
list is the precedence, and moving a rule is a behavioural change rather than a tidy-up.

## Preconditions

- At least two rules exist

## Main Success Scenario

1. The Power User moves a rule up or down.
2. The system reorders the list and writes it (UC-024).
3. The moved rule keeps the focus, so a second move needs no re-aiming.
4. The system announces the rule's new position, so the change is perceivable without sight of
   the list.

## Alternative Flows

### A1: The rule is already at the end it is moved toward

**Trigger:** The first rule is moved up, or the last down (step 1)
**Flow:**

1. The control for that direction is unavailable rather than inert, so the limit is visible
   before it is reached.
2. Nothing is written.

### A2: Rules are reordered faster than they can be written

**Trigger:** Several moves within the write interval (step 2)
**Flow:**

1. The system coalesces them and writes the resulting order once (UC-024 A5).
2. The order on screen is the order written.

## Postconditions

### Success Postconditions

- Storage holds the rules in their new order
- No rule's contents changed
- The moved rule holds the focus and its new position has been announced

### Failure Postconditions

- Storage holds the previous order
- The list on screen matches storage

## Business Rules

### BR-012-1: Reordering is operable from the keyboard, by construction

Moving a rule is a button per direction, not a drag. This is not an accommodation added to a
drag-and-drop interaction — it is the interaction.

The reference used `react-beautiful-dnd`, now deprecated by its own maintainers and carrying
known accessibility regressions, and a hand-rolled accessible drag is precisely the thing that
library existed to get right. NFR-019 requires WCAG 2.1 AA, and the cheapest way to satisfy it
here is to need nothing.

### BR-012-2: A move is announced, not merely rendered

A user who cannot see the list has to be told where the rule went. The new position is
announced when it changes, because a reorder that produces no perceivable feedback is a control
that appears to do nothing (NFR-019, NFR-020).

### BR-012-3: Order is stored as order

The rule list is an ordered sequence, and its position in that sequence is a rule's precedence.
There is no priority number to keep consistent with it, because two representations of the same
fact are one opportunity for them to disagree.
