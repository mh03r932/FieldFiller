# Use Case: Suspend Filling on an Excluded Domain

## Overview

**Use Case ID:** UC-008
**Use Case Name:** Suspend Filling on an Excluded Domain
**Primary Actor:** Tester
**Goal:** Make the extension do nothing at all on domains the user has listed, and say so when
asked
**Status:** Draft

Extends UC-001, UC-002 and UC-003.

**Traces to:** FR-037, FR-038, FR-074 · **Design:** DD-001, DD-006

"Inert on my banking site" is a trust property, and trust properties are worth more before a
product is shareable than after. That is why this lands with the scopes rather than with the
settings screen that configures it (implementation plan, Phase 3).

> **What this guarantees, stated before the scenario rather than after it.** No fill runs, no
> control is read, and nothing on the page is touched. **The page agent is still injected**, as
> it is on every page (DD-001) — it simply is never asked to do anything. FR-074 originally
> asked for more than this: that the code never be injected at all. That is achievable only by
> replacing the manifest's static declaration with runtime registration, and it was **considered
> and not taken on 2026-08-15** — see BR-008-4 for the reasoning and for what it costs.

## Preconditions

- The user has listed at least one domain pattern under exclusions
- The Tester invokes a fill on a page whose URL matches one of them

## Main Success Scenario

1. The Tester invokes a fill, at any scope, through any channel.
2. The system reads the URL of the tab it was asked to act on.
3. The system finds that the URL matches an exclusion pattern.
4. The system starts no fill operation: no message is sent to the page, no persona is created,
   and no control is examined.
5. The system marks the tab as excluded, and names the pattern responsible when asked.
6. The mark stays until the tab navigates elsewhere.

## Alternative Flows

*Ordered by the step whose failure or variation triggers them.*

### A1: The tab's URL cannot be read

**Trigger:** The system is not permitted to see the URL of the tab it was asked to fill
(step 2)
**Flow:**

1. The system treats the tab as excluded.
2. The system reports that it could not establish where it was being asked to act.

**Why exclusion is the safe direction:** the whole point of the list is that some pages must not
be filled. A fill that proceeds because the check could not run is the one failure mode this
use case cannot have. This is BR-005-1's reasoning applied to a page rather than a control.

### A2: The exclusion list is empty or unreadable

**Trigger:** No patterns are configured, or the stored list cannot be parsed (step 3)
**Flow:**

1. No URL matches, and the fill proceeds normally.
2. The use case does not apply.

**Note the direction is opposite to A1, and deliberately so:** an absent *list* is the default
state of a new install and means the user has excluded nothing. An absent *URL* is a failure of
the check itself. Treating "no patterns" as "exclude everything" would make the extension inert
out of the box.

### A3: A frame within the page is on an excluded domain

**Trigger:** The page is not excluded but one of its iframes is (step 3)
**Flow:**

1. The exclusion is evaluated against the **tab's** URL only.
2. Frames of the page are filled as usual.

**Stated because the alternative is tempting and wrong.** Evaluating per frame would mean the
extension reads the URL of every frame on every page to decide, which is more surveillance than
the feature is worth, and it would make "is this page excluded?" a question with several answers.
A user who wants a payment iframe left alone excludes the page that embeds it.

### A4: The user asks why nothing happened

**Trigger:** The Tester invoked a fill and saw no change (step 5)
**Flow:**

1. The toolbar shows a standing mark that this tab is excluded — not the transient count a
   completed fill leaves.
2. The tooltip names the pattern that matched, so the user can find and change it.

### A5: The tab navigates away

**Trigger:** The tab loads a different page (step 6)
**Flow:**

1. The system clears the mark.
2. The next invocation re-evaluates from scratch.

**How this is done without watching the user browse:** the system is told only that *a tab
changed*, never what it changed to. That is enough to clear a mark, and it is all this use case
needs (BR-008-3).

## Postconditions

### Success Postconditions

- No fill operation exists for the excluded tab
- No message was sent to any frame of that tab, and no control was read or written
- No persona was created, so nothing was generated and nothing needs discarding
- The toolbar states that the tab is excluded, and the tooltip names the pattern

### Failure Postconditions

- Not applicable: refusing to fill *is* this use case's success. A failure to determine the URL
  resolves to exclusion (A1), which is also a refusal.

## Business Rules

### BR-008-1: Exclusion is checked before anything else happens

The check runs before the persona is created and before any frame is contacted. An excluded
domain must not be able to observe that the extension exists by being asked a question, and a
fill that is decided against after work has begun is a fill that briefly began.

### BR-008-2: The URL is read only when the Tester invokes a fill

The extension does not watch the user browse. It learns a tab's URL at the moment it is asked
to act on that tab, through the permission that grants exactly that (`activeTab`), and it never
holds the `tabs` permission — which NFR-008 forbids by name because it reads the URL and title
of *every* tab.

The cost is that the mark appears when the Tester invokes a fill rather than standing whenever
they are on an excluded page. That matches what FR-038 actually asks for — *"so that I
understand why nothing happened"* — which is a question asked after trying.

### BR-008-3: Clearing the mark must not require knowing where the tab went

Navigation clears the mark, and the notification the system acts on carries the tab's identity
and its loading state, not its address. A design that re-evaluated on navigation would need
every URL, which is the surveillance BR-008-2 exists to avoid.

### BR-008-4: The guarantee is behavioural, not structural — and that is a choice with a cost

**Decided 2026-08-15.** FR-074 asked that an excluded domain mean the extension's code is never
injected there, so that exclusion is a statement about what *runs* rather than about what it
*does*. Delivering that means abandoning the manifest's static content-script declaration for
runtime registration with exclusions applied, and maintaining that registration across browser
starts, extension updates and every settings change.

That was not taken. The registration lifecycle is the kind of state that fails silently and in
the direction that matters — a missed re-registration means the agent is absent from pages the
user did want filled, or present on pages they did not. A static declaration cannot drift.

**What it costs, stated plainly rather than glossed:** on an excluded domain our code is still
loaded into every frame. It is never sent a fill instruction, it never walks the page, and it
holds no settings — but "the extension does not run on my banking site" is not true, and must
not be claimed. What is true is that it does nothing there. FR-074 was rewritten to say exactly
that, and the structural version is recorded here as available later without rework: the door
stays open, in the same way DD-001 left an opt-in narrower default open.

### BR-008-5: An excluded domain is excluded at every scope

The page, form and single-control scopes are all refused, through every trigger channel. A scope
chooses which controls a fill covers and nothing else (BR-001-6); it cannot be a route around a
decision about whether to fill at all.

### BR-008-6: A pattern matches a host, and the port takes no part

**Corrected 2026-08-16.** A pattern names a scheme, a host and a path, and the port the page
happens to be served on is not consulted — the same rule extension match patterns follow, and
the vocabulary this field claimed from the start. It did not follow it: `localhost/*` expanded to
a matcher that `http://localhost:3000/` failed, so an exclusion on any ported URL was accepted,
listed, and silently inert.

The direction is what makes it worth a rule rather than a fix. An exclusion that fails to match
fails **open** — the extension fills a site the user listed — and it does so with no signal at
all, because a pattern that matches nothing looks exactly like a page that was never excluded.
BR-008-1 puts this check before anything else happens precisely so that it is the one thing that
cannot be got wrong quietly.

A host typed with no path at all covers every path on it: `example.com` means `example.com/*`,
not "the root and nothing else". Someone typing into a field labelled "excluded domains" means the
domain, and the narrow reading would be the same silent failure in a different hat.

A port the user types is read as part of the host and then dropped, so `localhost:3000/*` covers
every port on `localhost`. Chrome would call that pattern malformed; voiding it would restore the
silent failure this rule exists to remove, and widening an exclusion is safe in a way that
voiding one is not. What a user cannot express is "this host on this port only" — recorded here
as a deliberate limit rather than left to be discovered, and reversible without rework if a real
need for it appears.

### BR-008-7: Matching a pattern is linear, and not a regular expression

**Added 2026-08-16.** A pattern is a list of literals that must appear in order, matched by
scanning forward once. It is deliberately not compiled to a regular expression, and the module
comment claiming as much described an intention rather than the code: `*` was translated to `.*`,
which is the textbook catastrophic-backtracking shape.

Measured before it was replaced, the pattern `*a*a*a*a*a*a*a*a*a*z` against a URL ending in a run
of `a`s took 3 ms at 20 trailing characters, 3.2 s at 40 and **33 s at 50**. BR-008-1 runs this
check before anything else happens on every fill, against a URL a page can make as long as it
likes, in the background — so the reachable form of this is every fill in the browser stopping.

Nothing reachable exploits it today, because a pattern can only be written into storage by hand.
UC-021 gives patterns an editor and UC-029 gives them import and sync, and a shared configuration
that stops every fill is not a failure worth shipping the ingredients for. Fixed before the
surfaces that would expose it, rather than after.

The same change removes the need to escape regular-expression metacharacters in a pattern, and the
per-fill compile step: there is no regex to build.

### BR-008-8: "I could not read the address" is not "you excluded this"

**Corrected 2026-08-16.** A1 and a real match both refuse the fill and both mark the toolbar, and
the implementation collapsed them by feeding a sentence into the slot the pattern goes in. The
tooltip then read *"Filling is off here — this page (its address could not be read) is on your
excluded list"*, which asserts a list entry that does not exist and sends the user to their
settings to look for it.

They are different facts and the user can act on only one of them. A pattern match is answerable —
A4 names the pattern precisely so it can be found and changed. An unreadable address is not the
user's doing and there is nothing in the list to go and look at; what A1 promises is that the
system says it could not establish where it was being asked to act. Each now has its own message.

The badge cannot carry this distinction — it reads `off` either way — so the harness asserts the
words, not the mark.
