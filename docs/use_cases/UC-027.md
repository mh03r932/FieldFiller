# Use Case: Migrate Settings from Fake Filler

## Overview

**Use Case ID:** UC-027
**Use Case Name:** Migrate Settings from Fake Filler
**Primary Actor:** Migrating User
**Goal:** Turn a Fake Filler backup into this extension's configuration, knowing exactly what
did not survive the translation — before the write
**Status:** Draft

Includes UC-024 (persist and propagate). Reads a file the reference wrote; nothing else in
this project does. Owes UC-026 A5's pointer: the settings importer refuses a Fake Filler
backup and says a converter is needed — this use case is that converter, and it sharpens the
importer's refusal to name it in the same change that builds this.

**Traces to:** FR-055, FR-056, FR-073 · PD-002, ND-13, DD-005

## Preconditions

- The Migrating User has the settings open
- The Migrating User has a backup file exported from Fake Filler

## Main Success Scenario

1. The Migrating User chooses to migrate, in the portability area of the settings screen, as
   its own control beside import — the two make different promises, and a control shared
   between them would blur which one is being made.
2. The system reads the file as text. Where the text is not itself JSON but decodes as the
   reference's transport — Base64 — the system decodes it and uses what it finds.
3. The system recognises the source by the keys the reference's documented schema carries.
4. The system translates the backup section by section and field by field into our schema,
   keeping two lists as it goes: everything that cannot be translated at all, and everything
   that translates with a loss or a change — a setting dropped off a rule that arrives, a
   template token with no equivalent, a bound ours must move.
5. The system shows both sides and the whole report **before** anything is written, in the
   shape UC-026 established: what is arriving and what it replaces; a list of what is dropped,
   each entry named with its reason; a separate list of what arrives changed, so the two
   promises — gone, and arriving-different — cannot be mistaken for each other.
6. The Migrating User confirms.
7. The system writes the translated state as a single replacement (UC-024).
8. The system confirms what landed, and the next fill uses it — in every open page, without a
   reload.

## Alternative Flows

### A1: The file is not a Fake Filler backup

**Trigger:** The text neither is nor decodes to JSON, or the JSON carries none of the
reference's documented keys (step 3)
**Flow:**

1. The system refuses the migration and says which of the two it was.
2. Where the file looks like *our* export, the system says so and points at UC-026 — the
   mirror of UC-026 A5, and the reason recognition runs on the reference's key set rather
   than on failure to parse ours.
3. Settings are untouched, and the refusal is dismissed like any other.

### A2: The backup states a version the translation was not written against

**Trigger:** The backup's `version` is not the documented one (step 4)
**Flow:**

1. The system translates it anyway, as the documented schema.
2. The report says so at its top: which version the file claims, which the translation was
   written against, and that a field whose *meaning* changed between them cannot be detected
   from here.

**Why not refuse, when UC-026 A2 refuses a newer file.** That refusal protects the only copy
of a user's configuration from being thinned on the way in. Here the source has its own copy
— the reference's own export still opens in the reference — and the documented schema has had
exactly one version since 2020, while the published extension is known to run ahead of its
public source (§4 of the research). Refusing every backup that might, hypothetically, differ
would block every real migrant to protect against a case that has never been observed. The
report is the net, and this flow is why it leads with the version it found.

### A3: A field translates only in part

**Trigger:** A field's type has a counterpart but its settings do not — an email field with
hostname or username customisation, a telephone or date template carrying tokens ours does
not have, a number bound ours must clamp (step 4)
**Flow:**

1. The rule arrives with the nearest generator and the settings that translate.
2. Every setting that did not survive is named on that rule in the report's second list, in
   the user's language — not as a count, as a sentence about the rule the user recognises.
3. The Migrating User confirms knowing what changed, or cancels.

**This is FR-056's heart.** A migration that drops a setting quietly has not migrated the
user's configuration; it has written a lookalike over it. The reference's email customisation
— a chosen hostname list, a chosen prefix — is real work the user did, and the report is the
only place it can be mourned usefully: the rule still arrives, and the sentence says what to
re-add if it mattered.

### A4: A translated rule fails the validation the editor applies

**Trigger:** A rule the translation produces is one the rule editor would refuse — most
plausibly a pattern that backtracks catastrophically (step 4; BR-026-8)
**Flow:**

1. The rule is not stored. It is named in the report's dropped list with the fault itself,
   worded as the editor words it.
2. The Migrating User confirms knowing what was refused, or cancels.

**The reference never screened a pattern in its life.** No ReDoS check exists anywhere in it,
and its matching is a list of arbitrary user regexes run against whatever identity text the
page holds. A backup is therefore the likeliest source of a pattern `validateRule` refuses
that this extension will ever see, and the migration is the last boundary it can be caught
at — after this, it is storage, and storage coerces rather than refuses (BR-024-7). BR-027-3
makes the join itself a place this can surface, which is why the fault names every pattern
that went into the rule.

### A5: A profile's URL match will not translate

**Trigger:** A profile carries a `urlMatch` regex, and ours matches URL glob patterns
(step 4)
**Flow:**

1. The profile arrives with its rules translated like any others, and **disabled**, with no
   URL patterns set.
2. The report names the profile and its pattern, and says the rules are inert until URL
   patterns are set on it.
3. Setting the patterns is one visit to the profile editor, from the report's own words.

**Not guessed, and not dropped.** A regex and a glob are different languages: `.*\.example\.com.*`
converts cleanly enough, `^(www\.)?(shop|checkout)\.` does not begin to, and a conversion that
is *sometimes* right is a profile that silently fires on the wrong pages — a behaviour change
on the importing machine wearing a successful migration's face (BR-027-5). Dropping the
profile would lose rules that translated perfectly well. Disabled is the honest middle:
nothing silently lost, nothing silently active.

### A6: A setting has no equivalent at all

**Trigger:** A section of the backup has no counterpart in our schema — the defined-mode
password string is the clean example (step 4)
**Flow:**

1. The setting is not carried. It is named in the dropped list with a reason that says what
   it was, not merely that it was not understood.

**The password case is worth its own sentence, because "dropped" is doing delicate work.**
The reference can fill every password field with one chosen string; our passwords are
generated under a policy and fitted to the field's own constraints (ND-11), and there is
nowhere in the schema to put a chosen string. The report must not let "not supported" read as
"not noticed": a QA workflow that relied on a known password is genuinely changed by
migrating, and the user should meet that fact in the report rather than at the login screen.

### A7: The write fails

**Trigger:** Storage rejects the replacement (step 7) — see UC-024 A2
**Flow:**

1. The previous configuration is still in force, whole.
2. The system says the migration did not happen.

### A8: The file is too big to be a backup

**Trigger:** The chosen file is larger than the bound UC-026 A9 established (step 1, before
step 2)
**Flow:**

1. The system refuses without reading the file, naming its size and the bound.

The bound and the reasoning are UC-026 A9's, not a new decision: the cost is the read and the
analysis, both on the options page's thread. A real backup is kilobytes — the reference caps
its free tier at twenty-five fields.

## Translation

The mapping, stated so the implementation derives from it rather than re-deciding it. Losses
named here are what step 5's report reports; absence from the loss column is deliberate and
means the mapping is exact (BR-027-4).

| The backup | Ours | What it costs |
|---|---|---|
| `fields[]` — one custom field | One rule, label from the field's name | — |
| `match: string[]` — regexes, any may match, case-insensitive | One `regex`-mode pattern | Nothing in principle; see BR-027-3 |
| Field matching scope | None set — the rule matches whatever the global sources allow | Nothing: the reference had no per-field scoping, and this reproduces its semantics exactly |
| `first-name` / `last-name` / `full-name` | `name` generator, part carried | — |
| `email` | `email` generator, persona on (BR-027-6) | `emailPrefix`, hostname and username customisation dropped, named per rule (A3) |
| `username`, `organization`, `url` | Direct counterparts | — |
| `telephone` | `telephone` generator, persona on | The template is dropped and named: ours draws from the persona |
| `number` with `min`/`max`/`decimalPlaces` | `number` generator with the same bounds | Bounds ours clamps are named as arriving changed |
| `date` with template and `minDate`/`maxDate` | `date` generator, `from`/`to` and `format` | Moment-style tokens translated token by token; tokens ours does not have pass through as literals and are named. Bounds translate when they parse as dates; otherwise the default range stands and the bound is named |
| `text` | `text` generator | A per-field `maxLength` has no word-count equivalent; our default sizing stands and the cap is named |
| `alphanumeric` template | `alphanumeric` template, token by token | Tokens with no exact counterpart — an uppercase consonant, a nonzero digit — map to the nearest placeholder and are named |
| `regex` | `regex` generator, the pattern as written | Whatever A4 refuses |
| `randomized-list` | `list` generator | — |
| `ignoredFields[]` | Field exclusions, `regex` mode | — |
| `agreeTermsFields` / `confirmFields` | `behaviour.consentKeywords` / `confirmationKeywords`, split on commas | — |
| `ignoreHiddenFields` / `ignoreFieldsWithContent` | `behaviour.skipHidden` / `skipPreFilled` | — |
| `triggerClickEvents` | `behaviour.dispatchEvents` | Behaviourally equivalent: both are "write with the interaction sequence" |
| `defaultMaxLength` | `behaviour.maxLengths`, set on the single-line kinds | The reference's single global cap is the defect ours replaces (ND-10): importing it verbatim would give an unconstrained textarea twenty characters. Textarea-sized kinds keep built-in sizing, and the report says so |
| `fieldMatchSettings` toggles | `sources` toggles, as the user set them | `matchAriaLabel` and `matchAriaLabelledBy` map to one source; if they disagree, ours is on and the split is named. Our test-automation source has no counterpart and stays at our default. `matchClass` is preserved as set — see BR-027-7 |
| `passwordSettings`, random mode | Password policy, length from the observed default | Character classes keep our defaults |
| `passwordSettings`, defined mode | Nothing | Dropped and named (A6) |
| `profiles[]` | Profiles, rules translated as above | `urlMatch` does not translate; the profile arrives disabled (A5) |
| `version` | Nothing carried | Reported (A2); ours writes its own |

## Postconditions

### Success Postconditions

- The stored configuration is the translation, valid under our schema as any authored
  configuration would be
- Everything the backup held that the translation could not carry was named to the user before
  the write, as a sentence about the thing the user recognises
- Everything that arrived different from the backup was named before the write, separately
  from what was dropped
- No part of the previous configuration survives except where the backup itself carried it

### Failure Postconditions

- The previous configuration is in force, complete and unchanged
- The reason the migration did not happen is stated, and it is never "some of it worked"

## Business Rules

### BR-027-1: A migration replaces; it never merges

The translation becomes the configuration (FR-055's "switch"). This is BR-026-1's rule with
one more reason to hold it: the incoming rules and the existing rules were authored in
different vocabularies, so a merged list would interleave two precedence orders nobody chose —
and precedence is behaviour (FR-031). A migrator who has already configured this extension
exports first; the screen's confirmation shows both sides precisely so that fact is visible.

### BR-027-2: The translation is written against the published schema, and says which one

The reference's documented schema is the only source this repository has, and the published
extension is known to run ahead of it (§4 of the research). The translation targets the
documented shape — a named commit and version, stated in the report — and A2's preamble covers
the gap. What this rule forbids is the quieter failure: a converter written from memory,
guessing at key names, which is inert when the guess is wrong and worse than inert when a key
name happens to be shared. UC-026's notes recorded that hazard when they left the pointer
unbuilt; this use case discharges it by reading the research rather than recalling it.

### BR-027-3: Several patterns become one rule, and the join is a validation boundary

The reference matches a field against a *list* of regexes, any of which may hit; our schema
applies one pattern per rule. The translation preserves the any-of semantics by joining the
patterns into one alternation — it does not split one field into several rules, because
several rules have an order nobody chose and a report that names one entry four times. Two
consequences follow, and both are obligations rather than notes: the joined pattern goes
through the same `validateRule` the editor applies (BR-026-8 — the reference never screened
these patterns, and joining them can surface what each hid); and when the join fails or is
refused, the report names every pattern that went into it, because "the rule" was the user's
whole list, not the one pattern that happened to tip it.

### BR-027-4: What maps exactly is stated as mapping exactly

Matching is case-insensitive on both sides — theirs by construction, ours in every mode by
decision — so a matcher's case-insensitivity carries over with no loss and no flag. The rule
names are part of both grammars. A mapping table that lists only its losses invites the user
to read silence as suspicion; the losses are trustworthy exactly when the non-losses are
visible (PD-002's obligation runs both ways).

### BR-027-5: Nothing is guessed into an active state

Where a translation cannot be faithful, it errs silent-proof: a profile that cannot be
brought whole arrives disabled (A5), a token with no equivalent becomes a literal that is
named, a setting with no home is dropped with its reason. The forbidden move is the plausible
conversion — regex to glob, character cap to word count — that is sometimes right and
silently wrong the rest of the time. A migration's report can absorb a named loss; it cannot
absorb an unnamed behaviour change, because nobody ever reads the report closely enough to
catch what it does not say.

### BR-027-6: Migrated persona-backed rules draw from the fill's person

The reference's generators are all freshly random; ours, given a persona-backed type, default
to the record's person (ND-1). A translated rule keeps that default. This is a deliberate
behaviour change from the reference, it is in the direction this product defines as correct —
the email a migrated rule writes still matches the name another field shows — and it is said
once, at the top of the report, rather than named on every rule. Setting it the other way
would make a migrated configuration a second-class citizen of coherence for no benefit the
migrant asked for.

### BR-027-7: The user's source toggles are preserved, including the ones we default off

Our `className` source ships off because it is the noisiest source to *author* against
(BR-018-2); the reference's ships on. A migration carries the user's setting as they set it.
Overriding an explicit choice with our default would be precisely the quiet configuration
loss this use case exists to prevent — and would leave the report in the absurd position of
naming the dropped email hostname while silently switching off half the matching the rules
depend on. The default is for blank slates; a backup is not one.

### BR-027-8: A key the translation cannot read is named once, and named where the loss falls

A backup is hand-editable text, so a documented key can arrive carrying the wrong kind of
value — `match` as a bare string, `min` as `"18"`, a literal past `1e308` that `JSON.parse`
hands over as `Infinity`. Three things follow, and they are one rule because getting any of
them wrong produces the same defect: a report the user cannot act on.

**Once.** Two checks ask different questions of the same key — is this the kind the schema
documents, and does this entry's type have a place for it — and a key documented for another
type fails both at once. Only the more specific answer is reported. Two lines for one fault
inflate the count the user is confirming, which is the one number in the whole flow they are
actually deciding on.

**Where the loss falls.** A mistyped key that costs a *setting* is named by path, and the
sentence says the default stands, because it does. A mistyped key that costs the whole
*entry* is named by field — which field, and inside which profile — because "this extension's
own default stands" is false about a rule that was never built, and a bare path does not tell
the user which of their fields they lost. One code cannot carry both sentences.

**Fatal only where the generator is built from it.** `template` on an `alphanumeric` field is
the generator; on a `date` field it is a format with a default behind it. `list` is the
generator for `randomized-list` and is a homeless key everywhere else. Where a key is
survivable when well-formed, it must not become fatal by being malformed — that holds the
hand-edited backup to a stricter standard than the clean one, and costs the user a rule whose
patterns, name and type were all perfectly readable.
