# Use Case: Configure Field Exclusions

## Overview

**Use Case ID:** UC-020
**Use Case Name:** Configure Field Exclusions
**Primary Actor:** Power User
**Goal:** Set the patterns and the structural rules that decide which controls are left alone
**Status:** Draft

Includes UC-024 (persist and propagate). Authors the configuration UC-005 applies.

**Traces to:** FR-034, FR-035, FR-036

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows the list of field patterns whose match leaves a control untouched, each
   with its match mode — contains, exact or regular expression.
2. The system shows the two structural skips beside them: controls that are not visible, and
   controls that already hold a value.
3. The Power User adds a pattern, changes one, or removes one.
4. The system stores the change (UC-024) and shows any problem with the pattern beside the
   field that caused it.
5. The next fill leaves every matching control exactly as it was, in every open page, without a
   reload.

## Alternative Flows

### A1: The pattern is not yet usable

**Trigger:** The pattern is empty, or is a regular expression that will not compile or that
backtracks catastrophically (step 3)
**Flow:**

1. The system states the problem beside the field, while the user is still typing.
2. An entry whose pattern is **malformed** is stored anyway.
3. An entry whose pattern is **blank** is not. The row stays on screen so it can be typed into,
   but it belongs to the page that created it and is gone by the next load: a blank pattern is
   not a half-written one, it is an entry the user has not begun, and storing it would keep a
   row that says nothing and can be abandoned by accident.
4. The agent skips an unusable pattern during a fill and applies the rest of the list
   (UC-005 A5).

Malformed patterns are stored, unlike an invalid *rule*, and the difference is where the
failure lands. An invalid rule is met by the engine during a fill on a page the user is not
looking at, so it is kept out of storage. An unusable exclusion is skipped with the rest of the
list intact, and refusing to store it would discard the half-typed pattern on every keystroke
that made it briefly invalid. That argument is about a pattern being *written*, which is why it
does not reach the blank one in step 3.

Empty is the one exception, because it is not unusable — it is usable and means the opposite of
what the user is reaching for. A `contains` pattern of `''` is contained in every field name
there is, and an empty regular expression matches every one of them too, so the blank row a
person creates by clicking "add" and then stopping would exclude the entire page rather than
nothing. Skipping it during a fill instead would work as well, but it would put a
match-everything pattern into storage and rely on every reader to keep declining it; refusing it
at the boundary means there is no such pattern to read (`parseMatcher`, and
`tests/exclusions.test.ts`).

What that costs is small and visible: a blank row exists only on the page that created it, so
reloading the settings before typing anything into it leaves nothing behind — which is the same
outcome as never having clicked "add".

### A2: A pattern matches more than the Power User meant

**Trigger:** A `contains` pattern of `name` also matches `username` and `company_name`
**Flow:**

1. Every matching control is left unfilled.
2. The fill report names each skipped control and why, which is where the user sees it.
3. The Power User narrows the pattern, or switches the entry to `exact`.

### A3: The list is empty

**Trigger:** The last entry is removed, or none was ever added
**Flow:**

1. The system states that every fillable control is a candidate.
2. This is the shipped default and a working configuration, not a missing one.

### A4: The change cannot be stored

**Trigger:** Storage rejects the change (step 4) — see UC-024 A2
**Flow:**

1. The previous list remains in force.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

## Postconditions

### Success Postconditions

- The stored list is what the Power User typed, in the modes they chose
- A control matching any usable entry is left exactly as it was, in every frame
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous list remains in force
- No control has been left half-excluded — a fill either applies the whole list or the previous
  one

## Business Rules

### BR-020-1: Exclusions carry the same three match modes rules do

`contains`, `exact` and `regex`, meaning exactly what they mean for a rule (FR-068). One
translation serves both, so a `contains` exclusion and a `contains` rule cannot drift into
meaning different things.

A pattern stored before this existed was a regular expression — that was the only vocabulary —
and is read back as one. Reading those as literal substrings would quietly change what every
exclusion an early user wrote actually excludes.

### BR-020-2: Order carries nothing

Unlike a rule list, where order is precedence (BR-009-2). Every entry is consulted and a
control is excluded if any of them matches, so a new entry is appended for predictability
rather than because the position means anything. The screen numbers them so that a person can
say "remove the third one", and nothing else.

### BR-020-3: An entry is removed by position, not by value

Two identical patterns are a redundant configuration rather than an illegal one. Removing "the
entry equal to this" would take the first of them however far down the list the user clicked.

The position is checked before it is used, because it can go stale: another copy of the settings
page may have shortened or reordered the list while this one was skipping the redraw that would
have taken the caret out of a row being typed into (BR-024-10). The same applies to editing a
row, and matters more there — a keystroke through a stale position rewrites an exclusion the
user never opened.

### BR-020-4: The two structural skips belong beside the list

`skipHidden` and `skipPreFilled` answer the same question the list does — which controls are
left alone — and a user looking for "don't touch this field" should find all three in one
place. They are not behaviour in the sense UC-022 means it: they decide which controls a fill
*picks*, not what it does to one it has picked.

### BR-020-5: Hidden controls are skipped by default and pre-filled ones are not

A hidden field that a person would never fill is how a honeypot catches a bot, and filling it
is what FR-071 exists to prevent — so that skip ships on.

Pre-filled is off, because the common case is filling the same form repeatedly with fresh data
(FR-075). Our own earlier writes never count as content either way (BR-005-7), so turning it on
does not stop a second fill of a form this extension filled.

### BR-020-6: A control excluded here is reported, not omitted

It appears in the fill report as skipped, with the reason. A control that simply does not
appear is indistinguishable from one the walk never found, and the difference is the whole
value of the report.
