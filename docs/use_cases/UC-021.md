# Use Case: Configure Domain Exclusions

## Overview

**Use Case ID:** UC-021
**Use Case Name:** Configure Domain Exclusions
**Primary Actor:** Power User
**Goal:** List the sites where the extension stays inert — loaded, but never asked to act
**Status:** Draft

Includes UC-024 (persist and propagate). Authors the configuration UC-008 applies.

**Traces to:** FR-037, FR-074

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows the list of address patterns on which every fill is refused.
2. The system states the vocabulary: `*` stands for any run of characters, everything else is
   literal, and the port takes no part.
3. The Power User adds a pattern, changes one, or removes one.
4. The system stores the change (UC-024) and shows any problem with the pattern beside the
   field that caused it.
5. On a matching page, every way of asking for a fill is refused before the persona exists and
   before any frame is contacted, and the toolbar marks the tab (UC-008).

## Alternative Flows

### A1: The pattern is not usable

**Trigger:** The pattern is empty, or contains whitespace (step 3)
**Flow:**

1. The system states the problem beside the field.
2. A pattern containing whitespace matches nothing, because an address contains none — so the
   system says that, rather than saying the pattern is malformed. It is well-formed and inert,
   which is the failure worth naming. It is stored, on UC-020 A1's terms.
3. A blank pattern is not stored, on the same terms. It matters more here than it does for a
   field exclusion: an empty domain list means "nothing is excluded" and is the reason a tab
   whose address cannot be read is still filled, so one abandoned blank row would make the list
   non-empty and refuse every such tab from then on — a fill that stops working, explained by a
   row with nothing in it.

### A2: The Power User excludes everything

**Trigger:** A pattern of `*` is typed (step 3)
**Flow:**

1. The system stores it. Every fill on every page is refused.
2. No warning is shown, and none is intended: there is no other global off switch, and refusing
   this would be the screen deciding what the list is for.

### A3: A pattern is briefly wider than the finished one

**Trigger:** `*.example.com/*` is typed one character at a time (step 3)
**Flow:**

1. Each keystroke is stored, so the list passes through `*`, `*.`, `*.e` and so on.
2. A fill invoked during those keystrokes is refused.
3. The next character narrows it. Nothing is left in a wrong state.

Accepted rather than designed around. The failure is *closed* — a page the user did not intend
to exclude declines to fill, and says so on the toolbar — and it corrects itself. Staging the
list behind a Save button would remove it at the cost of introducing a state in which what the
user sees and what a fill does disagree, which is the larger fault and the one UC-024's
postcondition rules out.

### A4: The page's address cannot be read

**Trigger:** A fill is invoked and the tab's address is unavailable (during a fill)
**Flow:**

1. The fill is refused, and the tooltip says the address could not be read — not that a pattern
   matched, because none did (UC-008 A1).
2. This use case has no part in it; it is UC-008's failure-closed direction.

### A5: The change cannot be stored

**Trigger:** Storage rejects the change (step 4) — see UC-024 A2
**Flow:**

1. The previous list remains in force.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

## Postconditions

### Success Postconditions

- The stored list is what the Power User typed
- Every fill on a matching page is refused, from every trigger, before any frame is contacted
- The toolbar names the pattern that refused it
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous list remains in force
- No page has been left half-excluded

## Business Rules

### BR-021-1: Inert means loaded and never asked, not absent

The page agent is present on an excluded page and is never spoken to. Not injecting at all was
the expected answer and was not taken: it needs runtime content-script registration in place of
the manifest's static declaration, and that registration is state which fails silently in the
direction that matters — an agent absent where the user wanted a fill, or present where they
did not (BR-008-4).

The consequence for this screen is that there are not two kinds of entry. Every pattern means
the same thing, so nothing here has to keep two tiers apart.

### BR-021-2: Globs, deliberately not regular expressions

The vocabulary users already know from extension match patterns. This check runs on a URL
before every fill, in the background, and a second catastrophic-backtracking surface there is
exactly where NFR-009 is hardest to guarantee — a shared or imported configuration that stops
every fill in the browser is not a failure worth shipping the ingredients for.

The matcher finds each literal segment with one forward scan and never goes back, so the
guarantee is structural rather than intended. There is correspondingly nothing on this screen
that can report an unparseable pattern, because there is no syntax to get wrong.

### BR-021-3: The port takes no part, on either side

`localhost/*` excludes `http://localhost:3000/`. Extension match patterns work this way and a
user typing a domain means the domain. Until 2026-08-16 ours claimed the vocabulary and did not
implement it, so an exclusion on any ported address was accepted, listed, and silently inert —
which is the failure this rule exists to name, because an exclusion that does not match fails
*open* and looks exactly like a site nobody excluded.

### BR-021-4: A pattern with no scheme matches any scheme

`example.com/*` covers both `http` and `https`. A user excluding their bank means the site, not
one protocol on it, and the version that made them write it twice would be the one they got
half right.

### BR-021-5: The refusal is visible

The toolbar shows a standing mark — cleared when the tab navigates, not after a few seconds —
and its tooltip names the pattern responsible. A fill that silently does nothing is
indistinguishable from a broken extension, and the pattern is named because "something excluded
this" sends the user to read a list they have to search by hand.

## Notes

The pattern-matching path has no end-to-end browser cover, and the reason is structural: the
address is read under `activeTab`, which follows a real user gesture and cannot be synthesised
by a harness. `scripts/e2e-settings.mjs` therefore drives this screen through the UI and
observes a real refusal, but the refusal it observes is A4's — the address could not be read.
The gap is recorded against FR-037 in `docs/requirements.md`, and it is why BR-021-3's defect
survived to a review rather than to a red build.
