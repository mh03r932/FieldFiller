# Use Case: Fill the Selected Input

## Overview

**Use Case ID:** UC-003
**Use Case Name:** Fill the Selected Input
**Primary Actor:** Tester
**Goal:** Populate exactly one control — the one the Tester pointed at — and nothing else
**Status:** Draft

Includes UC-004 and UC-005. Extended by UC-008 (excluded domains).

**Traces to:** FR-003, FR-004, FR-005, FR-006, FR-009, FR-010 · **Design:** DD-001, DD-008

The narrowest scope, and the one with the clearest intent: the Tester is topping up a single
field, usually after clearing it or after the page reset it. Everything about this use case
follows from that intent being unambiguous — there is nothing to infer, so nothing is inferred.

This scope is the reason DD-001 resolved the way it did. Chrome's `contextMenus.OnClickData`
carries `frameId` and `editable` but **no element identifier and no `getTargetElement`**, so
on-demand injection cannot know which control was right-clicked. A persistently injected agent
can, because it saw the event.

## Preconditions

- The Tester is viewing a page the extension is permitted to act on, and that page's domain is
  not excluded (UC-008)
- The page agent is present in that page's frames
- Settings are loaded

## Main Success Scenario

1. The Tester invokes "fill the selected input" over a control.
2. The system determines the **anchor**: the element the Tester pointed at, in the frame they
   pointed at it in.
3. The system classifies the anchor as fillable or excluded (UC-005).
4. The system determines and applies a value for it (UC-004).
5. The system verifies the write survived, and follows the page's reaction to it (UC-034).
6. The system reports one control's outcome, naming the scope as the single control.

## Alternative Flows

*Ordered by the step whose failure or variation triggers them.*

### A1: The anchor is not a fillable control

**Trigger:** The Tester invoked the scope over a paragraph, a disabled field, a honeypot, or
anything else the engine will not write (step 3)
**Flow:**

1. The system fills nothing.
2. The system reports the control as skipped, with the reason UC-005 gave — `disabled`,
   `hidden`, `not-fillable-kind`, and so on.
3. The use case ends.

**Why it refuses rather than looking nearby:** the Tester pointed at one thing and asked for
that thing. Filling the surrounding form does what they explicitly narrowed away from, and
filling "the nearest fillable control instead" is a guess whose result they cannot predict —
which DD-008 rejects for the form scope and which is worse here, where the intent is narrower.
An explicit narrowing is never widened (BR-002-2).

### A2: No anchor at all

**Trigger:** The scope was invoked by a keyboard shortcut with nothing focused and nothing
previously focused (step 2)
**Flow:**

1. The system fills nothing.
2. The system reports that there was no control to fill.

**Note the asymmetry with UC-002 A2**, and that it is the same rule underneath: the form scope
widens to the page when no intent was stated, because a superset of the right answer is still
useful. There is no superset of "one control" that is not a different scope entirely, so there
is nothing to widen to. Refusing is the only honest outcome.

### A3: The anchor is inside a frame

**Trigger:** The Tester right-clicked a control inside an iframe (step 2)
**Flow:**

1. The system directs the fill to that frame alone, identified by the frame the menu click
   reported.
2. No other frame takes part.
3. The use case continues at step 3.

### A4: The anchor belongs to a radio group

**Trigger:** The anchor is one radio button of a group (step 3)
**Flow:**

1. The system treats the **group** as the unit, not the button, and gives the group one answer
   (BR-005-3, BR-004-16).
2. Exactly one member ends up selected, which may not be the one pointed at.

**Why the group and not the button:** a radio button is not independently fillable. "Fill this
input" on one member can only sensibly mean "answer this question", and writing the pointed-at
button specifically would mean the Tester chose the value rather than the system.

### A5: The control disappears before the value arrives

**Trigger:** The page removes or replaces the anchor between the invocation and the write
(step 4)
**Flow:**

1. The system reports the control as failed, with the cause.
2. It does not search for a replacement: the anchor was an identity, and a different element in
   the same place is a different control (BR-034-4).

### A6: Filling the control changes the page

**Trigger:** The write causes the page to reveal, rewrite or enable other controls (step 5)
**Flow:**

1. The system verifies its own write survived, re-applying it if the page reverted it (UC-034).
2. **Controls the page revealed are not filled**, however clearly they depend on this answer.
3. The result names the scope, so a cascade the Tester can see happening but did not ask to be
   filled is explained by the scope rather than looking like a failure.

**Why the cascade is followed but not extended:** UC-034 exists to make a *write* stick, and
that applies at any scope. Filling what the page revealed would silently widen a scope the
Tester deliberately narrowed to one control, which is BR-002-2 again.

## Postconditions

### Success Postconditions

- The pointed-at control holds a value, or is recorded with a reason for not holding one
- **No other control on the page has been written**, including controls the fill revealed
- The result names the scope as a single control
- No form has been submitted and no navigation has occurred

### Failure Postconditions

- The control is left as it was found, or holds the value if the write partially succeeded and
  the result says so
- The result names the failure and its cause

## Business Rules

### BR-003-1: One control means one control

The scope is the anchor and, where the anchor is a radio button, its group. Nothing else is
read, written or reported on. A control revealed by the fill is outside the scope even though a
larger scope would have filled it.

### BR-003-2: The anchor is the element, not its position

The right-clicked element is remembered by identity for the page's lifetime, never by
coordinates or by selector. A page that re-renders between the right-click and the invocation
has replaced the control, and the fill fails rather than writing to whatever now occupies the
same place (A5).

### BR-003-3: The value is generated exactly as it would be at any other scope

A control filled alone receives the same value it would have received as part of a page fill
with the same operation seed, because generation is a function of the operation and the
control's token and of nothing else (FR-080, BR-004-15). Scope decides *which* controls are
filled, never *what* they are filled with (BR-001-6).

### BR-003-4: Coherence still applies, to a record of one

The fill draws from a persona exactly as any other fill does. One control is one field of a
coherent record, not an exception to the record — so a single-control fill of an email field
produces an address belonging to a person, not a random string. The persona is discarded with
the operation (NFR-031).

### BR-003-4: A frame element is never the anchor

**Added 2026-08-16.** When focus is inside an iframe, the *parent* document reports the
`<iframe>` element as its `activeElement`. A keyboard shortcut is routed to the top frame, so
without a guard the anchor for someone typing inside a frame was the frame itself: this scope
named an `<iframe>` as a control of an unfillable kind, and UC-002's scope resolved a container
around it and filled a form in the top document — the one document the user was demonstrably not
working in.

Frame elements are refused from every anchor source instead. The control scope then refuses with
"nothing to point at" (A2) and the form scope widens (UC-002 A2), which are both answers a user
can act on.

**What this does not do** is fill inside the frame the user was working in. Routing a shortcut to
the frame holding focus needs the background to know which frame that is, and no extension API
reports it. Recorded as a limit rather than left as a wrong answer: a shortcut used while typing
in a frame widens or refuses, and never fills somewhere else.
