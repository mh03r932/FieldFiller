# Use Case: Configure Password Generation

## Overview

**Use Case ID:** UC-019
**Use Case Name:** Configure Password Generation
**Primary Actor:** Power User
**Goal:** Choose the complexity policy a generated password starts from
**Status:** Draft

Includes UC-024 (persist and propagate). Constrains UC-004's password generation; constrained
in turn by UC-004's fitting to the field.

**Traces to:** FR-025, FR-026, FR-072

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows the policy a generated password starts from: a length, and which of
   uppercase letters, lowercase letters, digits and symbols it must include.
2. The system shows an example password produced by the policy as it currently stands.
3. The system states that a field's own `pattern`, `minlength` and `maxlength` are applied on
   top, and that the field wins.
4. The Power User changes the length or ticks a class on or off.
5. The system stores the change (UC-024) and replaces the example with one drawn from the new
   policy.
6. The next fill generates its password from the new policy, in every open page, without a
   reload.

## Alternative Flows

### A1: The Power User unticks every character class

**Trigger:** The last of the four classes is switched off (step 4)
**Flow:**

1. The system stores it, and states on the screen that with nothing ticked there is nothing to
   build a password from, so lowercase letters are used.
2. The example is drawn from that fallback, so what is shown is what a fill would produce.
3. The use case ends.

This is a state passed *through* on the way to another — unticking three to tick a fourth — so
refusing to store it would fight the user mid-edit. Saying what it does instead costs one
sentence and never blocks anything.

### A2: The length is smaller than the number of ticked classes

**Trigger:** A four-class policy is given a length of three (step 4)
**Flow:**

1. The system produces a password of the stated length, laying the classes down in order and
   cutting to length. The last classes are lost.
2. No warning is shown.

Length is what a form's own validation checks and composition is what it usually only
recommends, so length wins (BR-019-2). A warning here would fire on a state the user reaches by
typing a `2` on the way to `20`.

### A3: The field the password lands in constrains it further

**Trigger:** A password field carries `pattern`, `minlength` or `maxlength` (during a fill)
**Flow:**

1. The generated value is fitted to the field, keeping one character of each class it has.
2. Where the field's constraints cannot be met, the value is written anyway and the control is
   reported as failed rather than the fill claiming a value the page will reject (FR-076).
3. This use case has no part in it: policy loses to the page, always.

### A4: The change cannot be stored

**Trigger:** Storage rejects the change (step 5) — see UC-024 A2
**Flow:**

1. The previous policy remains in force.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

## Postconditions

### Success Postconditions

- The stored policy is what the Power User chose
- The example on screen was produced by that policy, by the generator a fill uses
- The next fill's password satisfies the policy, before the field's own constraints are applied

### Failure Postconditions

- The previous policy remains in force
- No password has been generated from a half-applied policy

## Business Rules

### BR-019-1: The policy is satisfied by construction, never by retrying

One character of each ticked class is laid down first and the remainder drawn from their union.
Generating repeatedly until a password happens to satisfy the policy is the obvious
alternative and it is unbounded against a policy the user can make unsatisfiable — which is a
hang, not a password.

### BR-019-2: Length wins over composition

Where both cannot be met, the value comes out at the stated length with classes missing rather
than at the required composition and the wrong length. A form checks length with an attribute
the browser enforces; composition it usually checks with a message.

### BR-019-3: The page always wins

Whatever this policy produces is fitted to the field's own `pattern`, `minlength` and
`maxlength` before it is written. A policy that could override the page would reintroduce ND-11
— a value the registration form rejects — through the settings screen, which is the one route
the fitter cannot see.

Fitting keeps one character of each class the password *has*, and never adds one it does not.
Topping a shortened password up to four classes was the behaviour before this use case existed;
it was harmless while every password came from one recipe and became wrong the moment the
policy was configurable, because it handed back exactly the class the user had switched off.

### BR-019-4: One password per fill, not one per field

The policy is applied when the persona is created, so every password field in a fill receives
the same value and a confirmation field agrees by construction (UC-006, ND-1). A policy applied
per field would generate two passwords and break the mirroring it is meant to be indifferent to.

### BR-019-5: The example is drawn from the real generator

Not a formatted illustration. A sample that came from a description of the policy rather than
from the code that implements it can disagree with what a fill produces, and the whole reason
to show one is that four checkboxes and a number do not tell a user what they will get.

### BR-019-6: Ambiguous characters are never emitted

No `l`, `I`, `1`, `O` or `0`, in any class. A tester reads these values off the screen and
retypes them, and a password that fails only because an `l` was read as a `1` costs exactly the
time the extension exists to save. Not configurable: there is no case for asking for ambiguity.

### BR-019-7: Nothing here reaches a log

FR-026 holds across this use case unchanged. The example on the options page is written to the
DOM of the extension's own page and nowhere else — not to a console, not to storage, and not
into the fill report, which records a password field's provenance and never its value.
