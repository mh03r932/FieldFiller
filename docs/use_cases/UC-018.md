# Use Case: Configure Field Matching Sources

## Overview

**Use Case ID:** UC-018
**Use Case Name:** Configure Field Matching Sources
**Primary Actor:** Power User
**Goal:** Choose which attributes take part in rule matching
**Status:** Draft

Includes UC-024 (persist and propagate). Bounds UC-004's rule selection and UC-009's per-rule
scoping.

**Traces to:** FR-027, FR-028, FR-029, FR-030, FR-083

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows the seven identity sources a rule may be matched against — the field's
   name, its id, its test id, its CSS class, its label text, its placeholder and its accessible
   name — and which of them are currently enabled.
2. The system states that these are a limit on every rule, not a default for new ones.
3. The Power User turns a source on or off.
4. The system stores the change and brings every running part of the extension into agreement
   with it (UC-024).
5. The system states how many sources are now enabled.
6. The next fill matches rules against exactly the enabled sources, in every open page, without
   a reload.

## Alternative Flows

### A1: The Power User turns off every source

**Trigger:** The last enabled source is switched off (step 3)
**Flow:**

1. The system stores it. This is a configuration, not an error.
2. The system states that no rule can now match anything, and that fields are still filled by
   the built-in generator.
3. The use case ends.

### A2: A rule names a source that is disabled here

**Trigger:** A rule carries its own source list (FR-067) naming a source switched off here
**Flow:**

1. The rule matches nothing through that source. The effective set is the intersection.
2. The system does not alter the rule, and does not report it as invalid.
3. The fill report names a rule that could not run, which is where the user finds out.

### A3: The change cannot be stored

**Trigger:** Storage rejects the change (step 4) — see UC-024 A2
**Flow:**

1. The previous set of sources remains in force.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

## Postconditions

### Success Postconditions

- The enabled sources are what the Power User chose
- Every rule's effective sources are the intersection of its own list with this one
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous set of sources remains in force
- No rule has been altered

## Business Rules

### BR-018-1: This is a bound, not a default

A source switched off here is off for every rule, including a rule that names it explicitly.
The effective sources of any rule are always the intersection of its own list with this one.

Stated on the screen in those words, because the alternative reading — that these are defaults
a rule can override — makes a rule that names `class` look like it should work. It would then
match nothing, silently, and look exactly like a rule with a bad pattern. Nothing else on the
screen distinguishes the two.

### BR-018-2: The CSS class ships disabled

It is the noisiest source by a distance: a utility-first stylesheet puts twenty meaningless
tokens in it and a component library puts its own vocabulary there. Shipped on, it produces
false matches on pages the user never looks at.

It is offered rather than dropped because the other half of real markup names its fields in
exactly that attribute and nowhere else. Deciding for everyone that class is untrustworthy is
the flattening ND-2 exists to prevent, made worse by being invisible.

### BR-018-3: Turning every source off is a legible state, not a broken one

It leaves every rule inert and the built-in generator untouched: fields are still filled, from
the persona and the `autocomplete` purpose, exactly as they were before rules existed. The
screen says so. An empty state that reads as damage is how a user comes to reinstall an
extension that was working.

### BR-018-4: `autocomplete` is not one of the seven

It is a controlled vocabulary rather than free text, and the generator already reads it
directly and ahead of any identity guess (FR-030). Offering it here as a seventh toggle would
invite rules that duplicate what the engine does better, and would let a user switch off the
single best identity signal a standards-compliant form gives.

### BR-018-5: The test id is one source over six attribute names, and ships enabled

There is no standard spelling, so the source reads `data-testid`, `data-test-id`,
`data-test`, `data-qa`, `data-cy` and `data-automation-id`, and takes the first one the field
carries. Six toggles — one per spelling — would be a settings screen about somebody else's
house style; a rule matching every `data-*` attribute would be the CSS class again, with the
provenance destroyed as well, since the report could not say which attribute the pattern hit.
One value per control keeps a pattern anchorable and the report honest (ND-2).

Which spellings are read is on the screen under the toggle. Without the list, deciding whether
this source does anything on your application means reading the extension's source.

It ships **on**, where the CSS class ships off, and for the mirror-image reason: the attribute
is only ever present because someone put it there deliberately, so it is silent on a page that
has none and it is frequently the only stable identity on a page that has them — a
component-rendered form routinely has a generated `id` (`:r3:`) and no `name` at all.

A configuration exported before this source existed names six sources. Its absence is read as
"not stated" and takes the shipped default, not as "off": off is a choice that user never
made, and it would quietly cost them the best identity on exactly the forms this source exists
for. That is BR-026-1's rule — what a file does not state takes the default — applied one level
down, to a key inside a section rather than to a section.

## Notes

The six toggles existed in the schema from DD-005 and bounded every rule from the day the rule
model was built; what did not exist until this use case was any way to set them. That is the
inversion recorded in the catalog under "Obligations Carried by Unwritten Specs" — the
constraint here was inherited, not chosen.

Amended 2026-08-22 by FR-083: a seventh source, the test-automation attribute. The screen's
shape did not change — one toggle, the same bound, the same count beneath it — which is the
argument for having built the section as a list over `MATCH_SOURCES` rather than as six
checkboxes somebody wrote out.
