# Use Case: Configure Triggers

## Overview

**Use Case ID:** UC-023
**Use Case Name:** Configure Triggers
**Primary Actor:** Power User
**Goal:** Control which ways of invoking a fill are available
**Status:** Draft

Includes UC-024 (persist and propagate). Routes to UC-030 for anything concerning keyboard
bindings.

**Traces to:** FR-006, FR-050, FR-005

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The system shows which invocation methods exist and which are currently available: the
   toolbar button, the context menu, and the keyboard.
2. The system shows the toolbar button as always available and offers no control to change
   that.
3. The Power User turns the context menu on or off.
4. The system stores the change and brings every running part of the extension into agreement
   with it (UC-024).
5. The system adds or removes the context menu entries, taking effect in already-open pages
   without a reload.
6. The system offers a route to the keyboard shortcuts view for anything concerning bindings.

## Alternative Flows

### A1: The Power User wants to change a keyboard binding

**Trigger:** The Power User follows the route offered in step 6
**Flow:**

1. The system opens the keyboard shortcuts view (UC-030).
2. This use case ends; binding is not something it can perform.

### A2: The change cannot be stored

**Trigger:** Storage rejects the change (step 4) — see UC-024 A2
**Flow:**

1. The previous setting remains in force and the context menu is left as it was.
2. The system reports that the change did not take effect, and why.
3. The use case ends.

### A3: A page cannot receive the change

**Trigger:** A page hosts no page agent — a browser-internal page, or one that loaded before
installation (step 5)
**Flow:**

1. The system skips that page without treating it as an error.
2. The context menu there resolves correctly the next time the page loads.

## Postconditions

### Success Postconditions

- The context menu is present or absent as chosen, in open pages and in pages opened later
- The toolbar button and the keyboard remain exactly as they were
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous trigger configuration remains in force everywhere
- No invocation method has been left half-configured
- The Power User has been told the change did not take effect, and why

## Business Rules

### BR-023-1: This surface signposts bindings; it never sets them

No extension can assign or change a keyboard binding — only the browser can, through its own
settings. Anything here that concerns bindings is a route to that settings page and must read
as one. A control that looks like it rebinds a key and merely opens a page is a lie the
interface tells, and the user only discovers it after their new binding does not work.

### BR-023-2: The toolbar button cannot be configured away

It is shown as an invocation method so the picture is complete, and it carries no control.
It is the zero-configuration path: a user who never opens these settings and never learns a
shortcut still reaches the product's main action in one click. Making it disableable would
allow a user to remove the only route that needs no setup, and to do it from a screen they
may not find their way back to.

### BR-023-3: Turning off one method never affects another

Disabling the context menu leaves the toolbar and keyboard untouched, and each method is
independently available. The methods differ only in which scopes they can reach
(BR-001-6), never in what a fill does.

### BR-023-4: Trigger changes take effect without a reload

A context menu turned off disappears from pages already open, and one turned on appears in
them. A setting that only applies to pages opened afterwards reads as broken, because the
page the user was looking at when they changed it is the one they check (FR-051).
