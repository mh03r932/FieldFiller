# Use Case: Delete a Custom Field Rule

## Overview

**Use Case ID:** UC-011
**Use Case Name:** Delete a Custom Field Rule
**Primary Actor:** Power User
**Goal:** Remove a rule that is no longer wanted
**Status:** Draft

Includes UC-024 (persist).

**Traces to:** FR-041

## Preconditions

- At least one rule exists

## Main Success Scenario

1. The Power User deletes a rule from the list.
2. The system removes it and writes the remaining list (UC-024).
3. The rules that followed it move up by one, keeping their relative order.
4. The system offers to undo the deletion, for as long as the options page stays open.

## Alternative Flows

### A1: The deletion is undone

**Trigger:** The Power User takes the undo offer (step 4)
**Flow:**

1. The rule is restored to the position it held, not to the end of the list.
2. The list is written again.

**Why the position is restored and not just the rule:** order is meaning here. A rule restored
to the end of the list is a different configuration from the one that was deleted, and the user
asked to undo, not to re-add.

### A2: The page is closed before the undo is taken

**Trigger:** The options page is closed or reloaded (step 4)
**Flow:**

1. The deletion stands. It was written when it happened.
2. No prompt is shown on the way out.

**Why deletion is immediate rather than staged behind a confirmation:** a confirmation dialogue
for every deletion is a thing to click through, and the thing it protects against — losing a
rule by accident — is better served by being able to put it back.

## Postconditions

### Success Postconditions

- Storage holds the list without the deleted rule
- Every remaining rule keeps its relative order
- The deletion can be undone while the page remains open

### Failure Postconditions

- Storage holds the complete list, including the rule
- The Power User has been told the deletion did not take effect

## Business Rules

### BR-011-1: Deleting is immediate and reversible, not confirmed and permanent

The deletion is written when the user asks for it, and an undo is offered rather than a
confirmation. A confirmation asks every user to prove intent every time; an undo asks nothing
and helps the one user in fifty who did not mean it.

### BR-011-2: Undo restores a position, not just a rule

See A1. Order is part of what a rule is, so restoring the rule without its position restores
something the user did not delete.
