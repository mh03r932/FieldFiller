# Use Case: Identify the Active Profile for a Page

## Overview

**Use Case ID:** UC-017
**Use Case Name:** Identify the Active Profile for a Page
**Primary Actor:** Browser
**Goal:** Resolve which profile governs a page, and tell the user which one did
**Status:** Draft

Included by UC-001, UC-002 and UC-003. Feeds UC-007.

**Traces to:** FR-047

## Preconditions

- A fill has been invoked on a tab

## Main Success Scenario

1. The system reads the tab's address, once, at the moment the fill is invoked.
2. The system takes the first enabled profile whose address patterns match it.
3. The system puts that profile's rules ahead of the global rules for this fill (UC-007).
4. The system records which profile applied, by name.
5. The fill report states which profile governed the fill — or that none did.

## Alternative Flows

### A1: No profile matches

**Trigger:** No enabled profile's patterns match the address (step 2)
**Flow:**

1. The fill runs on the global rules alone.
2. The report says that no profile matched, in words.

### A2: The address cannot be read

**Trigger:** The tab's address is unavailable (step 1) — see UC-008 A1
**Flow:**

1. No profile is resolved and the fill runs on the global rules alone.
2. The report says that no profile matched. It does not distinguish this from A1.
3. The fill is **not** refused.

### A3: The tab navigates during the fill

**Trigger:** The page changes after step 1
**Flow:**

1. The profile resolved at step 1 stands for the whole fill.
2. It is not re-resolved. The address was read under a grant tied to the invocation, and there
   is no right to read the new one.

## Postconditions

### Success Postconditions

- Exactly one profile, or none, governed the fill
- The rules that ran were that profile's followed by the global list
- The report names the profile that applied, or says none did

### Failure Postconditions

- Not applicable: there is no failing path. An address that cannot be read resolves to no
  profile, which is a valid outcome rather than an error.

## Business Rules

### BR-017-1: Resolution happens once, when the fill begins

Alongside the persona and the compiled rules, and for the same reason (BR-022-7): a fill spans
several passes and several frames, and re-resolving per batch would let one frame run a
profile's rules and the next not.

### BR-017-2: An unreadable address means no profile, never a refusal

The safe direction, and it is not symmetric with UC-008. An excluded *site* that cannot be
verified fails closed, because the point of that list is that some pages must not be filled.
A profile that cannot be resolved fails *open* — the fill runs with fewer rules — because
refusing would make every page whose address we cannot read unfillable the moment a user
created their first profile. That is a much larger failure than a fill that used the global
rules.

### BR-017-3: The indicator is a fill result, not a page indicator

FR-047 asks the Tester to be able to see which profile applies to the current page. What the
system can honestly offer is which profile *applied to the fill that just ran*, and the
difference is forced rather than chosen.

The extension learns a page's address only when a fill is invoked — that is what `activeTab`
grants and what keeps the `tabs` permission off the manifest (BR-008-2, NFR-008). An indicator
that showed the active profile *before* a fill would require watching the user browse, which
the extension does not do and whose absence is a stated guarantee. So the answer is given where
it can be given truthfully: in the fill report.

### BR-017-4: "No profile" is stated, not implied by silence

A fill that matched no profile says so. An absent line reads identically to a build that never
had profiles, and "did my scoped rules run?" is precisely the question FR-047 exists to answer —
silence cannot answer it, and the case where the answer is *no* is the case the user is most
likely to be checking.

### BR-017-5: The report carries the profile's name, not its identifier

It exists to be read. Nothing downstream needs the profile again.

A label is optional — UC-014 step 2 starts one blank — so "name" here means the same fallback
the profile list shows: the label, or failing that the first address pattern the profile
carries. A profile that governs a page always has one, because a profile matches only through a
non-empty pattern. Taking the label raw is what made BR-017-4 report the wrong answer: a
profile whose URL had been typed and whose name had not reported as blank, and a blank name is
indistinguishable from no profile at all — so the report announced that the user's global rules
had run alone while that profile's rules were in fact running ahead of them.

## Notes

**This use case has no end-to-end browser cover, and the reason is structural.** Resolution
needs the tab's address, which is granted by a real user gesture that a harness cannot
synthesise — so a harness-triggered fill reads no address and always takes A2. It is the same
gap FR-037's pattern path has, recorded against both.

What is covered: resolution, precedence and the value a control receives are asserted in
`tests/profiles.test.ts` by composing exactly what the background composes, and A1's report
line is asserted in a real browser by `scripts/e2e-profiles.mjs`. The untested remainder is the
three lines that join them.
