# Use Case: Create a Custom Field Rule

## Overview

**Use Case ID:** UC-009
**Use Case Name:** Create a Custom Field Rule
**Primary Actor:** Power User
**Goal:** Define a rule that gives a class of field the kind of value the Power User's own
application accepts
**Status:** Draft

Includes UC-013 (preview) and UC-024 (persist). Extended by UC-018 (matching sources).

**Traces to:** FR-039, FR-044, FR-067, FR-070 · **Design:** DD-005, ND-9, ND-2

The engine has had a rule model since DD-005 landed, and until this use case exists there is no
way to reach it that does not involve writing JSON into browser storage by hand. This is the
gap between built and usable.

## Preconditions

- The Power User has the options page open
- Settings have loaded

## Main Success Scenario

1. The Power User adds a rule.
2. The system creates it with defaults that do something sensible immediately — matching
   nothing yet, drawing from the fill's persona, and enabled — and opens it for editing at the
   end of the list.
3. The Power User names the rule, so the report can say which rule produced a value (FR-069).
4. The Power User writes what the rule matches: a pattern, and how to read it — as text the
   field's identity contains, as its exact identity, or as a regular expression (FR-068).
5. The Power User chooses what the rule generates, from the thirteen generator types, and
   fills in whatever that type needs.
6. The system shows sample output as the rule is edited (UC-013).
7. The system validates the rule on every change and writes it as soon as it is valid
   (UC-024, BR-009-1).
8. The rule takes effect on the next fill, in every open tab, with no reload (FR-051).

## Alternative Flows

*Ordered by the step whose failure or variation triggers them.*

### A1: The rule is not valid yet

**Trigger:** A pattern will not compile, a template names a placeholder that does not exist,
or a range starts after it ends (step 7)
**Flow:**

1. The system shows the problem beside the field that caused it, in the words FR-070's
   validation produced.
2. **Nothing is written.** The previously stored rule list stands.
3. The preview shows nothing rather than something wrong.
4. The use case resumes at whichever step the Power User returns to.

**Why nothing is written rather than written-and-flagged:** an invalid rule in storage is a
rule the engine will meet during a fill and have to skip, on a page and at a moment the user is
not looking at the options page. FR-070 exists to move that moment forward to now.

### A2: The pattern is dangerous rather than merely wrong

**Trigger:** A regular expression that compiles but can backtrack catastrophically (step 4)
**Flow:**

1. The system refuses it as in A1, saying which shape was recognised — a nested quantifier, a
   repetition of something that can match nothing, alternatives that overlap.
2. Nothing is written.

**Why it is refused at all:** a regex engine cannot be interrupted once it starts. In the
background context it would take the extension's only thread with it, and a fill that never
returns is indistinguishable from a hang (NFR-009).

### A3: The Power User leaves before the rule is complete

**Trigger:** The options page is closed while a rule is invalid (step 7)
**Flow:**

1. Whatever last validated is what is stored — which for a rule that has never been valid is
   nothing at all.
2. No draft is kept, and no warning is shown.

**Why there is no unsaved-changes prompt:** there is no unsaved state to warn about. Each valid
edit is already stored, so the only thing a prompt could protect is an edit the system has
already refused to keep (BR-009-1).

### A4: The generator type is changed after the rule was written

**Trigger:** The Power User switches a rule from one generator to another (step 5)
**Flow:**

1. The system keeps the rule's name, matcher, source scoping and persona flag.
2. Options belonging to the previous type are discarded, because they mean nothing to the new
   one — a date format is not a regex (ND-9).
3. The new type's own options appear with their defaults, and the rule is written as soon as
   it validates.

### A5: The rule matches nothing on any page

**Trigger:** A valid rule whose pattern simply never matches
**Flow:**

1. The system accepts it — this is not an error, and cannot be distinguished from a rule for a
   page the user has not visited yet.
2. The fill report names the rule only when it matches, so a rule that never fires is visible
   by its absence (FR-069).

## Postconditions

### Success Postconditions

- The rule is in storage, at the end of the list, and is the state the loader will read back
- It is valid: its pattern compiles, its template parses, and no known catastrophic shape is in
  it
- It applies to the next fill in every tab without a reload
- The Power User has seen sample output before it took effect

### Failure Postconditions

- Storage is unchanged and holds a complete, self-consistent rule list
- The problem is stated beside the field that caused it
- No partially formed rule exists anywhere

## Business Rules

### BR-009-1: A valid edit is saved; an invalid one is refused, not staged

There is no draft state and no Save button. Every change that validates is written immediately;
every change that does not is shown as a problem and not written.

This is what makes FR-070's "rejected when I save the rule" literally true — every keystroke is
a save, so every keystroke is where the rejection happens. It also removes the class of bug
where the page and storage disagree about what the user has configured, and the leave-warning
that class of bug requires.

### BR-009-2: A rule's order is part of its meaning

A new rule is created **last**, never first. The first matching rule wins (FR-031), so
inserting at the top would change the behaviour of every rule already written, silently, as a
side effect of adding an unrelated one. Last is the only position that changes nothing.

### BR-009-3: A rule is named by the user, for the report

The name is not decoration. It is what the fill report shows as a value's provenance, and what
identifies a rule that could not run (DD-005). A rule with no name given falls back to its
pattern, which is worse to read but never blank.

### BR-009-4: The preview draws from the real generators

Samples come from the same code the fill will run, not from a description of it. A preview
produced by a second implementation is a second thing to keep correct, and the first time the
two disagree is the moment the preview stops being worth having (UC-013).
