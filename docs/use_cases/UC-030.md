# Use Case: Review Keyboard Shortcuts

## Overview

**Use Case ID:** UC-030
**Use Case Name:** Review Keyboard Shortcuts
**Primary Actor:** Tester
**Goal:** See which fill scopes are bound to which keys, and reach the place where that can
be changed
**Status:** Draft

Reached from UC-023 or directly from the settings. Carries DD-007: one fill scope ships
deliberately unbound, which makes this view the only way a user learns it can be bound at all.

**Traces to:** FR-005, FR-060

## Preconditions

- The Tester has the settings open

## Main Success Scenario

1. The system asks the browser what is currently bound to each fill scope.
2. The system lists all three scopes — fill all inputs, fill this form, fill this input —
   each with the keys currently bound to it.
3. The system shows any scope with no binding as explicitly unbound, alongside the scopes
   that have one.
4. The system states that bindings are changed in the browser's own settings, not here.
5. The system offers a route to that settings page.
6. The Tester follows it.
7. The system opens the browser's shortcuts settings.

## Alternative Flows

### A1: A scope has no binding

**Trigger:** The browser reports no keys for a scope (step 3) — the shipped state of "fill
this input", and of any scope whose binding the user has cleared
**Flow:**

1. The system shows the scope with its name and an explicit "not assigned".
2. The system presents assigning it as an available action, routing to step 5.
3. The use case continues at step 4.

### A2: A shipped default did not take effect

**Trigger:** A scope shipped with a default reports no binding, or a different one, because
the browser declined to apply the suggestion — most often because another extension claimed
the combination first (step 1)
**Flow:**

1. The system shows what is actually bound, which may be nothing.
2. The system states that a suggested default exists and was not applied, so the user is not
   left believing the documentation is wrong.
3. The use case continues at step 4.

### A3: The user has changed a binding

**Trigger:** A scope reports keys that differ from the shipped default (step 1)
**Flow:**

1. The system shows the keys actually bound, with no warning and no suggestion to restore
   the default.
2. The use case continues at step 4.

### A4: The browser cannot report bindings

**Trigger:** The request in step 1 fails or returns nothing
**Flow:**

1. The system lists the three scopes without keys, and states that their bindings could not
   be read rather than that they are unbound.
2. The system still offers the route in step 5.
3. The use case continues at step 4.

### A5: The shortcuts settings cannot be opened

**Trigger:** The browser does not permit the extension to open its settings page (step 7)
**Flow:**

1. The system shows the address of that page so the Tester can reach it themselves.
2. The use case ends.

## Postconditions

### Success Postconditions

- Every fill scope is listed, whether or not it has a binding
- What is shown matches what the browser actually has bound
- The Tester knows bindings are changed in the browser, and how to get there
- Nothing has been changed by viewing this

### Failure Postconditions

- The Tester is told that bindings could not be read, rather than being shown an empty list
  that would read as "nothing is bound"
- The route to the browser's settings is still offered
- No binding has been altered

## Business Rules

### BR-030-1: Bindings are read from the browser, never from our settings

The user may have changed a binding, and another extension may have taken a combination
first. The browser is the only authority on what is bound, so this view asks it every time
rather than reporting what we intended to ship.

### BR-030-2: An unbound scope is shown, not omitted

Listing only bound scopes would hide the ones most needing attention. "Fill this input" ships
with no binding by decision (DD-007), and a user who cannot see the scope exists will never
bind it. This is exactly the reference's failure: it ships every scope unbound and prompts
nobody, so most of its users never assign a shortcut and never discover the feature.

### BR-030-3: The extension cannot assign a binding, and must not appear to

Only the browser can bind a key. Every action here leads to the browser's settings. Nothing
in this view may look like a field that accepts a key combination.

### BR-030-4: Shipped defaults are an intention, not a fact

A default is a suggestion the browser may decline, usually because another extension claimed
the combination. What is displayed is always what is bound now; where a suggestion was not
applied that is stated, so a user comparing this view with the documentation is not left
thinking one of them is wrong.

### BR-030-5: A user who cannot get a shortcut is not stuck

This view states that the toolbar button performs "fill all inputs" with no binding required.
A user whose keyboard is fully claimed by other software, or who simply does not want another
shortcut, still has the product's main action available (BR-023-2).
