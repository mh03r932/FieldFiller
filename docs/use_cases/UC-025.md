# Use Case: Export Settings to a File

## Overview

**Use Case ID:** UC-025
**Use Case Name:** Export Settings to a File
**Primary Actor:** Power User
**Goal:** Write the whole configuration to a file that can be diffed, reviewed and kept in
version control alongside the team's other configuration
**Status:** Draft

Reads the state UC-024 persists and changes nothing. Paired with UC-026, which reads back what
this writes — the two are one format seen from both ends, and a rule stated here binds there.

**Traces to:** FR-052 · ND-12 · NFR-008

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The Power User asks for an export.
2. The system takes the **stored** configuration — the state UC-024 last wrote, not what the
   screen is currently showing.
3. The system serialises it as pretty-printed JSON: the schema's keys in the schema's order,
   every list in its own order, text left as text.
4. The system hands the file to the browser to save, named for the extension and the schema
   version it holds.
5. The file is saved. Settings are untouched — an export is a read.

## Alternative Flows

### A1: The screen holds a change the user has not saved

**Trigger:** A rule is open in the editor with an edit in it, or a field has been typed into and
not committed (step 2)
**Flow:**

1. The system exports the stored state regardless, and says which it exported.
2. The unsaved edit stays on screen, unaffected.

The alternative — exporting what the screen shows — would put a state into a file that the
extension itself has never run, and the user would find it out on the machine they imported it
onto. What makes this safe to state plainly rather than to smooth over is that the file is
*named* honestly: the user who wanted the edit in the file saves it and exports again.

### A2: The browser refuses to save the file

**Trigger:** The save is cancelled, or the browser rejects it (step 4)
**Flow:**

1. Nothing has changed, because nothing was written to begin with.
2. The system says the export did not happen, and offers the same JSON to the clipboard.

The clipboard path is not a courtesy. `downloads` is a permission this project has refused
(NFR-008, gated by `check-permissions.mjs`), so an export leaves through an anchor and an object
URL created in the options page — a path the browser may decline for reasons the extension
cannot see and must not pretend to diagnose.

### A3: There is nothing configured yet

**Trigger:** The Power User exports the shipped defaults, having written no rules
**Flow:**

1. The system exports them anyway.
2. The file is a complete configuration, not an empty one — defaults are a state, and a file
   that restores "the extension as it ships" is a useful thing to keep.

### A4: The stored configuration cannot be read

**Trigger:** Reading storage fails (step 2)
**Flow:**

1. The system says the export did not happen and why, and offers the clipboard route — which
   reads the same way and will say the same thing.
2. No file is offered. Settings are untouched, because nothing was written.

The export reads storage strictly, and this flow is why. Everywhere else in the extension an
unreadable storage falls back to the shipped defaults: a fill must not stop because a preference
could not be read, and a page that cannot read settings shows the defaults rather than nothing.
An export cannot take that fallback. A file of defaults is a valid, complete, correctly named
configuration file, indistinguishable from a real one after the fact, and the user finds out
what it actually contained on the machine they import it onto — the same loss A1 protects
against, reached through the one door where nothing on screen would suggest it. So this is the
one read in the extension that is allowed to fail, and the failure is stated rather than
smoothed over.

## Postconditions

### Success Postconditions

- A file exists holding the complete stored configuration and the schema version it belongs to
- Settings are unchanged, in storage and in memory
- Re-exporting an unchanged configuration produces a byte-identical file

### Failure Postconditions

- No file is written
- Settings are unchanged, and the failure is stated rather than inferred from an absent file

## Business Rules

### BR-025-1: The export is the stored state, whole

Every section the schema defines is in the file — rules, profiles, exclusions, behaviour,
passwords, sources, triggers, locale — and the schema `version` with them. Not a subset, not a
diff against the defaults. A file that omits what happens to match the defaults is a file whose
meaning changes when the defaults do, and UC-026 would have no way to tell "the user chose this"
from "the user's version did not have this yet".

### BR-025-2: The file leaves without the `downloads` permission

NFR-008 forbids it and CI enforces that. The export is an anchor with an object URL, created and
revoked in the options page. This is written down because it is the kind of constraint that gets
discovered during implementation and worked around by asking for the permission.

The URL is revoked on a timer rather than after the click, and the timer is generous. The
download reads the blob through that URL, and how long the browser takes to do so is the
browser's business: Chromium resolves it during the click, Gecko has long resolved it
afterwards, and revoking first cancels the download with no error anywhere — the page has
already announced that the file was handed over. The cost of waiting is one blob held for a
minute; the cost of not waiting is a button that silently does nothing on an engine this project
ships for and does not test the export on.

### BR-025-3: An unchanged configuration exports byte-identically

No clock, no machine identity, no export counter, no key order that depends on how storage
happens to enumerate. The key order is the schema's, fixed in code; the list order is the user's.

The reason is ND-12's reason carried one step further: a file that differs on every export
cannot be kept in version control, because every export is a diff and none of them mean
anything. It is the same property `check-reproducible.mjs` holds the build to, for the same
reason — a digest that changes for no reason tells you nothing when it changes for a reason.

### BR-025-4: Pretty-printed, and readable in the language it was written in

Two-space indentation, one key per line, and non-ASCII text emitted as itself rather than as
`\uXXXX` escapes. A de-CH user's rule called `Kundenstraße` reads as `Kundenstraße` in the
diff. ND-12 rejected base64 because a backup nobody can read is not a backup; escaping every
umlaut is the same defect at a smaller scale, and this project ships a locale full of them.

### BR-025-5: Nothing in the file is a secret

The file carries a password *policy* — how long, which character classes — and never a password:
values are generated per fill and never stored (NFR-010, NFR-031). It carries no page content,
no visited address, no persona from any previous fill. This is stated so the screen can say it,
because "is it safe to commit this to a shared repository?" is the first question the feature
raises and the answer is yes.

### BR-025-6: The version travels with the configuration

The file states the schema version it was written against. UC-026 needs it to know whether it is
reading a state it understands, an older one to migrate, or a newer one it must refuse (ND-13),
and a file that omits it makes all three indistinguishable.

## Notes — what building it changed, 2026-08-22

Two things the flows above did not anticipate. Both are corrections to this spec rather than
notes about the implementation, which is why they are here and not only in the code.

**A2's clipboard route cannot be revealed by a failure, because the failure is not observable.**
As written, step 2 of A2 offers the clipboard *after* the browser refuses the file. Building it
showed that the refusal never reaches the page: the anchor's `click()` returns normally whether
the browser saves the file, prompts, or declines it outright, and nothing arrives afterwards. A
route offered only on failure would therefore be unreachable in exactly the case A2 describes.
Both routes are now standing offers side by side, and the announcement after a file export says
the settings were *handed to the browser* rather than *saved* — the strongest true statement
available, with a pointer to the clipboard if no file appeared. The flow is unchanged in what it
promises the user; what changed is that the promise is now keepable.

**BR-025-3's "no key order that depends on how storage happens to enumerate" is a live hazard,
not a hypothetical one.** `chrome.storage.local` hands the state back with its keys in
alphabetical order at every level — measured in `scripts/e2e-export.mjs`, after a harness
assertion that nothing had touched storage failed against a state nothing had touched. Every
configuration this extension exports has been through that round trip, so an exporter that
stringified what it read would have emitted a file in an order the schema never chose, and the
rule would have been broken by the storage layer rather than by anything in the export path.
The serialiser restates the schema's order itself for that reason.

**And one thing the flows got right in a way worth recording.** A1's "the screen holds a change
the user has not saved" was written for an edit in progress and reads as a rare case. It is not:
adding a rule creates one with an empty pattern, the tolerant parser drops exactly that on the
way into storage, and so the ordinary act of clicking Add puts the screen one rule ahead of the
file. The harness produces A1 that way rather than by contriving anything.
