# Use Case: Import Settings from a File

## Overview

**Use Case ID:** UC-026
**Use Case Name:** Import Settings from a File
**Primary Actor:** Power User
**Goal:** Replace the configuration with one from a file, knowing before the write what will be
kept and what will not
**Status:** Draft

Includes UC-024 (persist and propagate). Reads what UC-025 writes. A *Fake Filler* backup is
not this use case — that is UC-027, and A5 below is how the two are kept apart rather than
silently confused.

**Traces to:** FR-053, FR-054, FR-073 · ND-13

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The Power User chooses a file.
2. The system reads it as text and parses it as JSON.
3. The system reads the schema version the file states, and decides what it is looking at: the
   current schema, an older one to migrate, or one it cannot reach.
4. The system coerces the file into the current schema, keeping a list of everything it could
   not keep — a rule with no usable pattern, an unknown generator type, a section that is not
   the shape the schema expects — and of every rule it *could* read that FR-070 will not let it
   store.
5. The system shows what the import will do **before** it does it: how many rules and profiles
   the file brings, what will be replaced, and every entry that was dropped, named.
6. The Power User confirms.
7. The system writes the imported state as a single replacement (UC-024).
8. The system confirms what landed, and the next fill uses it — in every open page, without a
   reload.

## Alternative Flows

### A1: The file is not our format

**Trigger:** The file is not JSON, or is JSON that is not an object (step 2)
**Flow:**

1. The system refuses the import and says which of the two it was.
2. Settings are untouched.
3. The refusal can be dismissed, which discards the file and imports nothing. This is true of
   every refusal below and is not restated in each.

### A2: The file states a version newer than this extension knows

**Trigger:** `version` is greater than the current schema version (step 3)
**Flow:**

1. The system refuses the import, naming both versions.
2. There is no "continue anyway" (ND-13).
3. The system says what would fix it — a newer version of the extension — because the user's
   next move is otherwise to edit the version number in the file by hand, which is the bypass
   with extra steps.

A newer file is refused rather than coerced, and the asymmetry with A3 is deliberate. Coercing
an older state *adds* what was not there yet, and the defaults it adds are knowable. Coercing a
newer one *discards* what this version cannot name, and neither the extension nor the user can
see what was lost — the file is the only copy, and it would be silently thinned on the way in.

### A3: The file states an older version

**Trigger:** `version` is less than the current schema version (step 3)
**Flow:**

1. The system migrates the file's state forward to the current schema and continues at step 4.
2. The migration is not optional and cannot be skipped (ND-13).

**What stands here today is not the ladder FR-073 asks for.** DD-005 accepted a tolerant parser
in the ladder's place, and it is what this step would use: it coerces any input into a valid
state per field and drops what it cannot read. For an *additive* change it is indistinguishable
from a migration step — Phase 4's `triggers` section and the two keyword lists defaulted
correctly when absent, tested rather than assumed. For a *structural* one it is not a migration
at all, it is a silent loss, and the only thing that separates the two here is step 5 naming
what was dropped. The ladder is what makes the naming unnecessary; until it exists, the report
is what keeps the loss visible rather than silent.

### A4: The file is from before the schema had sections

**Trigger:** The file states no version at all (step 3)
**Flow:**

1. The system reads it as the pre-DD-005 flat shape, which the parser already lifts — the
   behaviour keys sat at the top level and their leaves did not move.
2. The import continues at step 4 with everything else defaulted.

### A5: The file parses, and nothing in it is ours

**Trigger:** The file is a JSON object with no key the schema recognises — most likely a Fake
Filler backup (step 4)
**Flow:**

1. The system refuses the import rather than applying it.
2. Where the file looks like a Fake Filler backup, the system says so and points at UC-027.

**This flow exists because the tolerant parser would otherwise succeed.** Given an object it
does not recognise, it returns a complete, valid, *default* configuration — so a user importing
their Fake Filler backup would be told the import worked, and would have lost every rule they
had. An import that recognises nothing is not an empty configuration; it is the wrong file, and
those two must not produce the same outcome. This is the one place where the tolerance that is
right for storage (BR-024-3: on any doubt, something usable) is wrong at the boundary.

### A6: The file brings less than it appears to

**Trigger:** Some rules or profiles cannot be kept (step 4), either because the file could not be
read or because BR-026-8 will not store what it says
**Flow:**

1. Every dropped entry is named in step 5, by its label and pattern, before anything is written.
2. A rule refused under BR-026-8 is named with the fault itself, worded as the editor words it,
   because nothing is wrong with the file's syntax and "could not be read" would send the user to
   correct the wrong thing.
3. The Power User confirms the import knowing the count, or cancels.

### A7: The write fails

**Trigger:** Storage rejects the replacement (step 7) — see UC-024 A2
**Flow:**

1. The previous configuration is still in force, whole.
2. The system says the import did not happen.

## Postconditions

### Success Postconditions

- The stored configuration is exactly the file's, migrated to the current schema
- Every entry the file held and the import did not keep was named to the user before the write
- No part of the previous configuration survives except where the file itself carried it

### Failure Postconditions

- The previous configuration is in force, complete and unchanged
- The reason the import did not happen is stated, and it is never "some of it worked"

## Business Rules

### BR-026-1: An import replaces; it never merges

The file's configuration becomes the configuration. Rules are not appended to the existing list,
profiles are not matched up by label, and a section absent from the file does not keep its
current value — it takes the file's, which for a well-formed file means the file's default.

Merging would produce a state that neither the file nor the user ever authored: a rule list in
an order nobody chose, with precedence — and precedence is behaviour here, since first match
wins (FR-031). It is the same argument BR-024-1 makes for writing settings whole rather than
patching them, at the scale of a whole configuration.

### BR-026-2: There is no bypass

No "load anyway", no "ignore the version", no partial import of the parts that validated. ND-13
names the reference's bypass as the defect; the way a bypass gets built is one refusal at a time,
each with a good local reason, so the rule is stated once for all of them.

Dismissing a refusal is not one of them, and the distinction is worth stating because it is the
one a future change is likely to blur. A bypass takes the file the system refused and imports it
anyway. Dismissing throws that file away and imports nothing — it exists because the refused
file is otherwise held and re-analysed on every redraw, so a settings change in another tab
brings the refusal back and only a reload clears it. A control that ends with nothing written is
not a way past a rule that only concerns what may be written.

Nor is BR-026-8, and the wording above is worth reading carefully next to it. "No partial import
of the parts that validated" is about a file the system *refused*: none of it may be smuggled in
one section at a time. A file that is not refused has always brought less than it says — A6 is
the flow for it — and a rule dropped there is dropped in full, named before the write, with no
control offered that would keep it.

### BR-026-3: Tolerance at the boundary must be reported, tolerance in storage need not be

The same coercion runs in both places and the obligation differs. Reading storage, dropping a
malformed rule silently is right: the alternative is a user with no settings at all, and the
state being read is one this extension itself wrote. Reading a file, the same silence is data
loss — the file may be the user's only copy, and it was written by something else, possibly by a
different version, possibly by a colleague. So step 5 exists, and it runs before the write
rather than after it: a report after the fact tells the user what they can no longer recover.

### BR-026-4: What is not recognised at all is refused, not applied

Stated as its own rule because A5's failure is invisible in every part of the system except this
one: the parse succeeds, the write succeeds, the screen refreshes, and the configuration is
gone. The check is on the way in — a file yielding no recognised section is not an import.

### BR-026-5: The user sees both sides before confirming

What is there now, and what the file brings, in the same sentence: rules, profiles, and the
count of what will be dropped. An import is the most destructive action in the settings screen
and the only one whose damage is invisible until the next fill on a page the user cares about.
UC-028 requires a confirmation to restore defaults; replacing a configuration with a stranger's
warrants no less.

### BR-026-6: All of it or none of it

The write is one replacement (UC-024), so a failure leaves the previous configuration whole.
There is no state in which half a file has been imported, and no flow that writes rules first
and sections after.

### BR-026-7: Unknown keys inside a known version are dropped, and said

A file at the current version may still carry keys this build does not know — hand-edited, or
written by a build from a branch. They are not stored, and they are named in step 5 with
everything else that was dropped, so "I added that by hand and it did nothing" is answerable.

This holds at every depth the schema defines, not only at the root. `profiles[0].rules: 42` is a
profile that arrives with no rules in it, `profiles[0].urls: "https://x/*"` a profile that
matches no page, and `rules[0].sources: "name"` a rule that arrives matching *every* source
instead of the one it names — all three well-shaped enough to import, and each one a change of
behaviour on the importing machine that no count in step 5 accounts for.

A key the build *does* know, holding a value of a kind the schema does not keep there, is
reported the same way and separately worded: the name was recognised, the value was not, and
what took its place is the built-in default rather than nothing. `{"behaviour": 3}` replaces
every behaviour setting, and a report that stayed silent about it would be describing that
import as clean. The expected kind is taken from the shipped defaults, which hold a value of the
right kind everywhere the schema defines one, so this cannot drift from the schema.

The check is on *shape*, not on content. A value of the right kind that the parser still cannot
use — an unknown locale, an exclusion whose regex will not compile — is coerced silently, and
naming it needs the migration ladder A3 is waiting for rather than a second copy of the parser's
rules in the import analysis. A rule FR-070 refuses is the one exception, and it is not a
counter-example: BR-026-8 does not coerce it, and it asks the same function the editor asks
rather than restating anything.

### BR-026-8: A file may not store a rule the editor would refuse

FR-070 rejects a rule when it is saved rather than when a page is filled, and the importer is the
only other writer of rules. Every rule the parser reads out of a file is put to the *same*
`validateRule` the editor uses; one that fails it is not stored and is named in step 5 with its
fault.

This is a safety rule before it is a consistency one. NFR-009 keeps catastrophic backtracking off
the fill path, and that path is where a pattern is at its most dangerous: `compileRules` compiles
each rule once per fill and `selectRule` runs it against identity text the *page* controls, in
the background worker. A file carrying `(a+)+b` was well-shaped, imported clean, and wedged the
next fill on a page that chose the input — while the editor refused the same six characters
beside the field they were typed into.

Field exclusions are deliberately outside this rule. Their editor stores a pattern while it is
still invalid, on purpose (UC-005 A5): a half-typed pattern is invalid on the way to being valid,
and refusing it would lose the keystroke. Validating them on import would make a file stricter
than the screen that authors them, which is a different defect rather than a fix — and it would
mean an exported configuration that could not be imported back.

## Notes — what building it changed, 2026-08-22

**A5's second step is not built as written, and deliberately.** The flow says that where the
file looks like a Fake Filler backup, the system says so and points at UC-027. Recognising one
means knowing the reference's backup key names, and nothing in this repository records them —
§7 describes the reference's *behaviour*, PD-002 its grammars, neither its storage shape. A
detector written from memory would be a claim nobody measured: inert if the guess is wrong, and
worse than inert if a key name happens to be shared. So the refusal says only what it can prove
— nothing in this file is a setting this extension knows — and adds that a backup from a
different form filler needs a converter this version does not have. **The pointer at UC-027 is
owed and unbuilt**, and belongs to UC-027 anyway: that is the use case which will have read the
reference's schema, and it can sharpen this message in the same change. The protective half of
A5, which is the half that matters, is built and tested.

**A5's trigger is implemented as BR-026-4 words it, not as the flow words it.** The flow says "no
key the schema recognises"; the rule says "no recognised *section*". They differ over `version`
alone, and the rule is right: `version` describes a configuration rather than carrying one, so a
file holding nothing else carries no setting to apply. Were it enough to make a file ours, any
file that happened to use the same key name would import a complete set of defaults over the
user's configuration and report success — the exact outcome A5 exists to prevent, reached
through the one key most likely to be shared. `{"rules": []}` is accepted, because an empty rule
list is a configuration someone can have meant.

**A7 could not be honoured through the writer the page already had.** Every other change on this
screen is saved optimistically and fire-and-forget: memory takes it, storage is written, and a
rejection is announced after the fact (UC-024 A2). An import cannot work that way, because A7
requires the *importer* to know — the previous configuration is still in force, the import did
not happen, and the plan has to stay on screen to be tried again. So the page gained one
operation that reports whether its write landed, used by nothing else.

**BR-026-8 was owed and unbuilt until 2026-08-24, and two files in this repository said it was
already done.** `lib/rules/validate.ts` stated that its checks run "in the options page (Phase 4),
in the importer (UC-026, UC-027)", and the settings store warned that "a future writer that is not
the editor has to validate for itself" — the importer being exactly that writer. It did not: it
asked `parseSettings` about shape and nothing about validity, so a hand-edited or borrowed file
could store a rule the editor refuses, including a catastrophically backtracking pattern that
`compileRules` then compiled into the fill path. Closing it needed no new judgement about what a
valid rule is, only the existing `validateRule` applied on the way in — which is why the fix is
small and why the gap was easy to miss: every part of the system except the importer already
behaved as though the rule existed.

**BR-026-7's promise was root-deep, and the report read as though it were not.** The shape check
compared each root section against the shipped defaults, which hold no rule and no profile to
compare a nested field against, so `rules[0].sources: "name"` and `profiles[0].rules: 42` passed
through it in silence and imported as behaviour changes with a clean report over them. What was
missing was a witness, not a rule: feeding the parser one minimal rule and one minimal profile
and keeping what it hands back gives a shape to compare against that cannot drift from the
schema, which is the same argument the section-level check already made about `DEFAULT_SETTINGS`.

**And one thing the spec was right about in a way worth recording.** BR-026-3's claim that the
same tolerance is correct in storage and wrong at the boundary is not a stylistic preference —
it is the whole reason this use case needs a module of its own. `parseSettings` has no failure
mode: handed a Fake Filler backup it returns a complete, valid, entirely default configuration.
Every refusal above exists because the layer underneath cannot refuse anything, and the analysis
that names dropped entries had to be built as an *observer* of that parser — each entry put to
it one at a time — rather than as a second opinion about what it would do. A second
implementation is how the preview and the write come to disagree, which is BR-024-7's hazard at
the scale of a whole configuration.
