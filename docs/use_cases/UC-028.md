# Use Case: Restore Default Settings

## Overview

**Use Case ID:** UC-028
**Use Case Name:** Restore Default Settings
**Primary Actor:** Power User
**Goal:** Return the whole configuration to the shipped defaults, knowing what is being
discarded before it is gone
**Status:** Draft

Includes UC-024 (persist and propagate). Sibling of UC-026: both replace the whole
configuration in one write — this use case's source is the running build rather than a file,
which is why it needs a confirmation rather than a preview. UC-029, once built, carries the
restore to other devices through the same included write; nothing here has to know it exists.

**Traces to:** FR-048, FR-057

## Preconditions

- The Power User has the settings open
- Current settings are loaded

## Main Success Scenario

1. The Power User chooses to restore defaults, in the portability area of the settings screen
   beside import and export.
2. The system states what restoring means, in counts: how many rules, profiles, field
   exclusions and domain exclusions will be discarded, and that every behaviour, password,
   matching-source and trigger setting returns to its shipped value.
3. The system names the way back — export (UC-025) — in the same confirmation, before the
   write rather than after it.
4. The Power User confirms.
5. The system writes the shipped defaults as a single replacement (UC-024).
6. The system confirms what landed, and the next fill uses the defaults — in every open page,
   without a reload.

## Alternative Flows

### A1: The Power User cancels

**Trigger:** The confirmation is dismissed (step 4)
**Flow:**

1. Nothing is written and nothing is held. The use case ends with the configuration exactly
   as it was.

### A2: There is nothing to discard

**Trigger:** Every count in step 2 is zero and every section already holds its shipped value
**Flow:**

1. The system says so in the confirmation.
2. The restore is still offered. A replacement of the current state by an identical one is
   harmless, and "prove this installation is clean" is a legitimate thing to want — a
   defaults-only configuration is the state the extension ships in, not an error (BR-028-4).

### A3: The write fails

**Trigger:** Storage rejects the replacement (step 5) — see UC-024 A2
**Flow:**

1. The previous configuration is still in force, whole.
2. The system says the restore did not happen, and why.

### A4: A fill is running when the restore lands

**Trigger:** A fill operation is in progress in some tab (step 5)
**Flow:**

1. Nothing is required of this use case. A fill carries the settings it was invoked with
   (BR-024-6), so the running fill completes under the configuration the user saw when they
   triggered it, and the next fill in any tab uses the defaults.

## Postconditions

### Success Postconditions

- Storage holds exactly the shipped defaults, with no element of the previous configuration
  surviving anywhere the extension controls
- The in-memory settings and the compiled patterns match what is stored
- Context menu presence reflects the stored state
- No open tab required a reload
- The previous configuration continues to exist exactly where the user put it, and nowhere
  else: an export file, if one was made

### Failure Postconditions

- The previous configuration is in force, complete and unchanged
- The reason the restore did not happen is stated, and it is never "some of it worked"

## Business Rules

### BR-028-1: A restoration replaces; it never merges

The shipped defaults become the configuration. No rule, profile, exclusion or setting is
carried over from the previous state. This is BR-026-1's argument at its limit: precedence is
behaviour, so a merge would produce a rule order nobody chose, and "keep my rules but reset
the rest" is not a state this screen should invent unasked. A user who wants that can export
first, restore, and import back the parts they meant to keep — through surfaces that show
both sides.

### BR-028-2: The confirmation quantifies the loss

"Are you sure?" with no numbers is a ritual, not a consent. The confirmation names the counts
of what will be discarded and the sections that reset, because the damage a restore does is
invisible until the next fill on a page the user cares about. BR-026-5 asks the same of an
import; discarding one's *own* configuration rather than a stranger's file warrants no less
(FR-057).

### BR-028-3: The defaults are the running build's

What is restored is what the installed build ships, read from the same definition a first
install uses — not a remembered ideal. Two consequences, both worth a sentence here so the
screen is not asked to imply them: a restore on an older build yields that build's defaults,
and after an update the defaults may legitimately differ from the ones the user remembers, so
a restore is not an undo of the update.

### BR-028-4: The shipped default is a defaults-only configuration, and that is the product

FR-048 asks for "a useful default rule set on first install", and the honest form of that is
narrower than its written form — the third such requirement in this project, after FR-047 and
FR-074. The rule list ships empty on purpose (DD-005): an unmatched field falls through to the
persona-driven generator, so a user who writes no rules gets the full engine — every control
kind, native constraints, coherent person, dependent fields. The usefulness FR-048 asks for
lives in the engine, and the empty counts on A2's confirmation screen are the shipped state
working as designed, not a defect. Recorded here so nobody "fixes" the empty list by shipping
starter rules nobody asked for.

### BR-028-5: There is no undo, and the way back is offered before the write

Every other destructive action in the settings screen offers an undo (UC-011, UC-015) because
its loss is one entry. A restore discards the whole configuration at once, and the honest
instrument is different in kind: export, offered in the confirmation itself. An undo window
would mean the extension retaining the replaced configuration — a second state, held on a
timer, that a later write must remember to supersede — and the settings store holds one state
by design (BR-024-1). The confirmation says plainly that there is no undo, in the same breath
as it names export, so the choice is made with both facts.

## Notes — what building it changed, 2026-08-24

**A2's "every section already holds its shipped value" became a parser-normalised comparison,
and that sharpened it.** The check compares the state through `parseSettings` against the
shipped defaults, so a state that differs only by what the parser drops — a rule with an empty
pattern, the state between adding a rule and typing its pattern, or junk keys from a hand
edit — *is* the shipped configuration and is told so. A raw comparison would have put a count
of one rule on a confirmation about to say nothing is discarded, which is the exact
disagreement BR-028-2 exists to prevent. This is the same discipline the options page's own
storage listener applies to the same question (BR-024-3), and it is why the check lives in
`lib/restore.ts` rather than in the section: the counts and the already-defaults answer are
one fact about one state, and two places computing it is how they drift.

**The counts follow the import preview's convention: a profile counts once and carries its
rules.** The spec names four counts and does not say where a profile's rules belong; the
build puts them inside the profile count, because `importPlanSummary` words its two sides
that way and a confirmation is not the place to invent a fifth number that splits one fact
across two. A user with three profiles of twenty rules reads "3 profiles" and knows what
losing them costs.

**Nothing else moved.** Step 5 is the import's `replace` verbatim — the page already had a
write that settles when storage has and rolls memory back when it has not, and reusing it is
what makes A3 true rather than aspirational. A4 needed no code at all, which is BR-024-6
being load-bearing two use cases away from where it was written. The e2e harness
(`pnpm run restore:chrome`) drives the confirmation through a real browser on both sides of
every click; `tests/restore.test.ts` holds the counts and the already-defaults semantics,
with the empty-pattern case named as its own test so the narrowing above cannot be
optimised away as a bug.

## Notes — what review changed, 2026-08-24

**Opening the confirmation dropped the focus on `<body>`.** The entry button's handler
re-rendered the section, which destroyed the focused control — the exact outcome this page
refuses everywhere else it removes a control ("starting again from the top of the page"), and
inside the one flow whose second click is destructive. The focus now moves to the cancel
button: a real target, and the safe action, so Enter does not sit one keystroke from
committing a write the user has only started to read. Tab reaches confirm from it in one
move. The e2e harness asserts it structurally, as `activeElement` matching `.restore-cancel`
the moment the plan appears.

**`isDefaultConfiguration` compared one parsed side against an unparsed literal.** The
comment claimed both sides went through the parser, as BR-024-3's listener does; the code
compared parser output against `DEFAULT_SETTINGS`' own key order. Correct today, because the
literal and the parser happen to emit in the same order — and silent the day they stop,
in the benign direction nobody notices: A2's "already are the shipped ones" line would
quietly never render. Both sides are parsed now, and a regression test holds the invariant
by feeding the check both a parser-emitted state and a key-reordered one.

**The confirmation shipped unaudited.** The a11y harness passed with the new section
present, but never opened the confirmation — so the surface the use case exists for, and
the longest substituted string on the page, had been through neither colour scheme nor the
320 px reflow check. It is now audited as its own state (`restore-confirm`, both schemes)
and left standing through the reflow and text-resize checks on purpose, then cancelled.
