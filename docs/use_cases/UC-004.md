# Use Case: Determine the Value for a Field

## Overview

**Use Case ID:** UC-004
**Use Case Name:** Determine the Value for a Field
**Primary Actor:** *(none — included subfunction of UC-001, UC-002, UC-003, UC-013)*
**Goal:** Produce a plausible value for every fillable control in a fill scope, coherent
across the whole scope, and write it so the page registers the change
**Status:** Draft

The heart of the system. Extended by UC-006 (confirmation fields) and UC-007 (URL profiles).

**Traces to:** FR-011, FR-012, FR-013, FR-019..FR-023, FR-025, FR-027..FR-032, FR-065..FR-069

## Preconditions

- The fill scope has been determined and its controls classified by UC-005
- Current settings are loaded and their rule patterns already validated and compiled
- At least one control survived exclusion

## Main Success Scenario

1. The system builds a descriptor for each fillable control, carrying its kind, its identity
   from each enabled matching source separately, its declared autocomplete purpose, and its
   native constraints.
2. The system submits the descriptors for the whole scope as one batch.
3. The system synthesises **one persona** for this fill — an internally consistent fictional
   person with identity, contact, address and account details.
4. For each descriptor, the system selects the first rule whose pattern matches, giving
   profile rules precedence over global rules.
5. Where no rule matches, the system selects a default generator from the control's
   autocomplete purpose if declared, otherwise from its kind.
6. The system draws each value from the persona where the generator names a persona
   attribute, and generates a fresh value otherwise.
7. The system constrains each value to the control's declared limits, and to the rule's own
   limits where narrower.
8. The system returns the values with, for each one, the rule that matched and the source it
   matched on.
9. The system writes each value so that scripts owning the control observe the change.
10. The system dispatches the interaction sequence appropriate to the control's kind.
11. The system records each control's outcome and provenance in the fill report.

## Alternative Flows

### A1: No rule matches and the control's kind has no meaningful default

**Trigger:** Steps 4 and 5 yield no generator
**Flow:**

1. The system generates a short neutral text value sized for the control's kind.
2. The use case continues at step 7.

### A2: Control offers a fixed set of choices

**Trigger:** The control is a select, radio group, or otherwise constrained to enumerated
options (step 6)
**Flow:**

1. The system determines the value the generator would produce.
2. If an enabled option matches that value, the system selects it.
3. Otherwise the system selects a random enabled option, skipping a leading placeholder
   option whose value is empty.
4. The use case continues at step 9.

### A3: Generated value cannot satisfy the control's constraints

**Trigger:** The value violates a declared limit that cannot be met by trimming (step 7)
**Flow:**

1. The system retries generation up to a bounded number of attempts.
2. If no attempt satisfies the constraints, the system records the control as failed with
   the reason "constraints unsatisfiable" and leaves it untouched.
3. The use case continues with the next descriptor.

### A4: Generation for one field fails or exceeds its time budget

**Trigger:** A generator throws, or exceeds the per-field generation budget (step 6)
**Flow:**

1. The system abandons that field only.
2. The system records the control as failed with the cause.
3. The use case continues with the next descriptor. **The run is never abandoned.**

### A5: Background context was evicted before the fill

**Trigger:** The batch in step 2 arrives at a background context that is not yet running
**Flow:**

1. The system starts the background context and loads the corpus.
2. The use case continues at step 3, within the cold-start budget.

### A6: Control owns its value through a framework

**Trigger:** Writing the value directly would not be observed by the script controlling the
control (step 9)
**Flow:**

1. The system writes the value through the control's own value mechanism so the owning
   script observes it.
2. The use case continues at step 10.

### A7: Event dispatch is disabled in settings

**Trigger:** The user has turned off interaction events (step 10)
**Flow:**

1. The system writes values without dispatching the interaction sequence.
2. The use case continues at step 11.

### A8: Control holds rich editable content rather than a value

**Trigger:** The control is a content-editable region (step 9)
**Flow:**

1. The system replaces its textual content.
2. The use case continues at step 10 — content-editable regions receive the same event
   sequence and the same exclusion checks as any other control.

## Postconditions

### Success Postconditions

- Every fillable control in the scope holds a value, or is recorded as failed with a cause
- All values drawn from persona attributes agree with one another across the whole scope
- Every value satisfies the control's declared constraints
- The fill report names, for each control, the rule that matched and the source it matched on
- The persona and all generated values are discarded when the fill completes, unless the user has explicitly asked for the persona to carry across fills (NFR-031)
- No generated value has been written anywhere other than its target control

### Failure Postconditions

- Controls processed before the failure retain their values; the fill is not rolled back
- The failure and its cause are recorded in the fill report
- No partially written value is left in any control

## Business Rules

### BR-004-1: One persona per fill, not one per field

A fill synthesises a single fictional person and projects it onto the scope. Every
persona-derived field in that scope draws from the same record, so the name, the email built
from it, the postcode and the city agree by construction rather than by correlation
(ND-1, FR-023).

### BR-004-2: A persona is internally consistent

Address components agree — postcode belongs to the locality, locality to the region, region
to the country. Phone format matches the country. Email and username derive from the name.
Consistency is a property of the persona, not something reconstructed per field.

### BR-004-3: A new fill means a new persona, unless continuity is asked for

By default persona state does not survive a fill: filling the same form twice produces two
unrelated people, which is what makes repeated submission useful for testing (FR-075).

The exception is reserved rather than exercised. A user may later be given a way to carry one
persona across several fills — a multi-step form needs the same person on every step. That is
permitted by NFR-031 because a persona is data the extension *invented*, not data it took
from a page. Retaining a persona is therefore a different act from retaining page content,
which NFR-010 forbids outright and unconditionally. Nothing in this design may assume a
persona is single-use.

### BR-004-4: First match wins, profile before global

Rules are evaluated in user order; the first match is used and evaluation stops. Profile
rules are evaluated before global rules. Order is the user's control surface, so it must be
honoured exactly and never reordered by specificity (FR-031).

### BR-004-5: Matching sources stay separate

Each matching source is matched against independently, never as one concatenated string.
This is what lets a pattern be anchored, keeps a class attribute from triggering a rule
intended for a name, allows a rule to be scoped to particular sources, and makes it possible
to report which source matched (ND-2, FR-067, FR-068, FR-069).

### BR-004-6: Label text is rendered text

A control's label contributes the text a user reads, never the markup that produces it, and
labels that wrap their control count equally with those referencing it by id
(ND-3, FR-029, FR-066).

### BR-004-7: The control's own constraints are a ceiling

A rule may narrow what the control declares; it may never widen it. Where a rule and the
control disagree, the stricter limit applies. A generated value that the page's own
validation would reject is a defect, not a rule the user chose (FR-012).

### BR-004-8: Interaction is simulated honestly

The event sequence matches what the control's kind would really produce — focus before
change, change before blur, and a click only for controls a user actually clicks. Announcing
a click on a text input is a lie the page may act on (ND-6, FR-013).

### BR-004-9: Generated values are never disclosed

No generated value — passwords above all — is written to a console, to storage, or to any
destination other than its target control. The reference logs generated passwords into the
page's console (ND-5, FR-026).

### BR-004-10: Descriptors carry identity, never content

A descriptor states what a control *is*, never what it currently holds. Nothing needs a
field's existing value to choose a generator, and not collecting it is what keeps the
privacy claim structural rather than promised (NFR-030).

### BR-004-11: One field's failure is one field's failure

Every field is generated and applied in isolation. A malformed pattern, an unsatisfiable
constraint or a hostile page cannot end the run (FR-010). The reference lets a single throw
abandon the remainder of the page (ND-10 / D10).

### BR-004-12: Generation is seedable

Given a fixed seed and a fixed set of descriptors, generation produces identical values.
Randomness is a runtime default, not a property of the design — without this, the engine's
behaviour cannot be asserted in a test (NFR-012, NFR-013).
