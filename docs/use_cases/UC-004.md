# Use Case: Determine the Value for a Field

## Overview

**Use Case ID:** UC-004
**Use Case Name:** Determine the Value for a Field
**Primary Actor:** *(none — included subfunction of UC-001, UC-002, UC-003, UC-013)*
**Goal:** Produce a plausible value for every fillable control in a fill scope, coherent
across the whole scope, and write it so the page registers the change
**Status:** Draft

The heart of the system. Extended by UC-006 (confirmation fields) and UC-007 (URL profiles).

**Traces to:** FR-011, FR-012, FR-013, FR-019..FR-023, FR-025, FR-027..FR-032, FR-065..FR-069,
FR-080

## Preconditions

- The fill scope has been determined and its controls classified by UC-005
- Current settings are loaded and their rule patterns compiled once for the whole fill, never
  per control per rule (NFR-025). Patterns are validated when the rule is saved (FR-070), but
  that is not assumed here: a rule can arrive by import or sync without passing through the
  authoring path, and A11 covers one that cannot run
- At least one control survived exclusion

This use case may be entered more than once for the same fill, and more than once for the same
control, because the page can change in response to being filled (UC-034). Nothing below may
depend on being the first entry, and step 6's answer may not depend on how many entries
preceded it.

## Main Success Scenario

1. The system synthesises **one persona** for this fill operation — an internally consistent
   fictional person with identity, contact, address and account details — before any control
   is examined, and keeps it available for the operation's lifetime.
2. The system builds a descriptor for each fillable control, carrying its kind, its identity
   from each enabled matching source separately, its declared autocomplete purpose, its
   native constraints, and a token that names the control for the operation's lifetime.
3. The system submits the descriptors it currently has as one batch, naming the fill operation
   they belong to. A batch is the controls that need a value *now*, not the scope: on a page
   that cascades there are several, and each carries only what the previous one could not
   have covered.
4. For each descriptor, the system selects the first rule whose pattern matches, giving
   profile rules precedence over global rules.
5. Where no rule matches, the system selects a default generator from the control's
   autocomplete purpose if declared, otherwise from its kind.
6. The system draws each value from the persona where the generator names a persona
   attribute, and otherwise derives one from the operation and the control's token — so the
   same control asked again in the same fill is answered the same way (BR-004-15).
7. The system constrains each value to the control's declared limits, and to the rule's own
   limits where narrower.
8. The system returns the values with, for each one, the rule that matched and the source it
   matched on.
9. The system writes each value so that scripts owning the control observe the change.
10. The system dispatches the interaction sequence appropriate to the control's kind.
11. The system records each control's outcome and provenance in the fill report.

## Alternative Flows

*Ordered by the step whose failure or variation triggers them.*

### A1: The background context is not running when the fill begins

**Trigger:** The fill operation begins while the background context is stopped, which is its
normal state between uses (step 1)
**Flow:**

1. The browser starts the background context, which loads the data corpus.
2. Once the corpus is available the use case continues at step 1, within the cold-start
   budget.

### A2: No rule matches and the control's kind has no meaningful default

**Trigger:** Steps 4 and 5 yield no generator
**Flow:**

1. The system generates a short neutral text value sized for the control's kind.
2. The use case continues at step 7.

### A3: Control offers a fixed set of choices

**Trigger:** The control is a single select, a multi-select, a radio group, or otherwise
constrained to enumerated options (step 6)
**Flow:**

1. The system determines the value the generator would produce.
2. If an enabled option matches that value, the system selects it and continues at step 9.
3. Otherwise the system takes the eligible options to be those that are enabled and whose
   value is not empty — wherever a placeholder sits in the list, and however many there are.
4. For a single select or a radio group, the system selects one eligible option at random.
5. For a multi-select, the system selects a random subset of the eligible options, at least
   one and at most all of them, each chosen at most once.
6. If no option is eligible, the system records the control as skipped with the reason "no
   selectable option" and leaves it untouched.
7. The use case continues at step 9.

### A4: Generation for one field fails or overruns its budget

**Trigger:** A generator throws, or its evaluation exceeds the per-field budget (step 6)
**Flow:**

1. The system abandons that field only.
2. The system records the control as failed with the cause, noting an overrun where the
   budget was exceeded.
3. The use case continues with the next descriptor. **The run is never abandoned.**

### A5: Generated value cannot satisfy the control's constraints

**Trigger:** The value violates a declared limit that cannot be met by trimming (step 7)
**Flow:**

1. The system retries generation up to a bounded number of attempts.
2. If no attempt satisfies the constraints, the system records the control as failed with
   the reason "constraints unsatisfiable" and leaves it untouched.
3. The use case continues with the next descriptor.

### A6: Control owns its value through a framework

**Trigger:** Writing the value directly would not be observed by the script controlling the
control (step 9)
**Flow:**

1. The system writes the value through the control's own value mechanism so the owning
   script observes it.
2. The use case continues at step 10.

### A7: Control holds rich editable content rather than a value

**Trigger:** The control is a content-editable region (step 9)
**Flow:**

1. The system replaces its textual content.
2. The use case continues at step 10 — content-editable regions receive the same event
   sequence and the same exclusion checks as any other control.

### A8: A control is described again during the same fill

**Trigger:** A control that already received a value is submitted in a later batch, because the
page wiped it, replaced its options, or replaced the element itself (step 3) — see UC-034
**Flow:**

1. The system determines the value exactly as it would for a control it had not seen, with no
   memory of the earlier answer and no record of what was written.
2. Because the answer is a function of the operation and the control's token, and of nothing
   else, it is the same answer (BR-004-15).
3. Where the control's own constraints have changed — most often a select whose options were
   rewritten — the answer is drawn from what the control offers *now*, which may differ. A
   value chosen from a list the page has discarded is not an answer.
4. The use case continues at step 7.

### A9: Event dispatch is disabled in settings

**Trigger:** The user has turned off interaction events (step 10)
**Flow:**

1. The system writes values without dispatching the interaction sequence.
2. The use case continues at step 11.

### A10: A matching rule cannot produce a value this control can hold

**Trigger:** A rule matched at step 4, but its value is not something this control could take —
it names an option the control does not offer, or the control is a checkbox or a custom
combobox, which have no text to write and no published options to match against (step 6)
**Flow:**

1. The system discards the rule's value for this control.
2. The system continues as though no rule had matched, from step 5.
3. The control's provenance names the generator that actually answered it.

**Why it degrades rather than fails:** the rule was about *which* value, and a rule naming an
option the page does not offer has nothing to honour. A filled field beats an empty one, and the
alternative — leaving the control untouched because the user's rule was out of date — punishes
the user for a change the page made.

### A11: A rule cannot be run at all

**Trigger:** A stored rule's pattern will not compile, or its template or generator pattern is
malformed (step 4). FR-070 rejects these when the rule is saved, so reaching here means the rule
arrived another way: imported, restored from a backup, or synced from a device running a newer
version
**Flow:**

1. The system skips the rule and continues evaluating the remaining rules in order.
2. The fill proceeds normally; the control is answered by the next matching rule, or by the
   default generator.
3. The system names the skipped rule and the reason in the fill result.

**Why it is reported rather than ignored:** a rule that silently does nothing is
indistinguishable from a rule that did not match, and the user has no way to discover which.
That is the reference's behaviour and one of the defects this product exists to correct.

## Postconditions

### Success Postconditions

- Every fillable control in the scope holds a value, or is recorded as failed with a cause
- All values drawn from persona attributes agree with one another across the whole scope
- Every value satisfies the control's declared constraints
- The fill report names, for each control, the rule that matched and the source it matched on
- A control asked for twice within one fill received the same answer both times, unless the
  control's own choices changed between the asks (FR-080)
- The persona and all generated values are discarded when the fill completes, unless the user has explicitly asked for the persona to carry across fills (NFR-031)
- No generated value has been written anywhere other than its target control

### Failure Postconditions

- Controls processed before the failure retain their values; the fill is not rolled back
- The failure and its cause are recorded in the fill report
- No partially written value is left in any control

## Business Rules

### BR-004-1: One persona per fill, not one per field

A fill synthesises a single fictional person and projects it onto the scope. Every
persona-derived field in that scope draws from the same record, so the name, the email built
from it, the postcode and the city agree by construction rather than by correlation
(ND-1, FR-023).

### BR-004-1a: The persona precedes the descriptors

The persona is created when the fill operation begins, not assembled from what the page turns
out to contain. It is complete whether or not the page has an address field, and descriptors
only decide which of its attributes get projected where.

This is what makes a fill spanning several frames possible without coordinating them. Frames
cannot talk to each other, and a fill that had to gather every frame's descriptors before it
could invent a person would need a barrier, a timeout, and an answer for frames that report
late or never. Creating the persona first removes all three: each frame independently sends
its descriptors, names the operation, and receives values drawn from a person who already
exists (BR-001-1).

### BR-004-2: A persona is internally consistent

Address components agree — postcode belongs to the locality, locality to the region, region
to the country. Phone format matches the country. Email and username derive from the name.
Consistency is a property of the persona, not something reconstructed per field.

### BR-004-3: A new fill means a new persona, unless continuity is asked for

By default persona state does not survive a fill: filling the same form twice produces two
unrelated people, which is what makes repeated submission useful for testing (FR-075).

The exception is reserved rather than exercised. A user may later be given a way to carry one
persona across several fills — a multi-step form needs the same person on every step. That is
permitted by NFR-031 because a persona is data the extension *invented*, not data it took
from a page. Retaining a persona is therefore a different act from retaining page content,
which NFR-010 forbids outright and unconditionally. Nothing in this design may assume a
persona is single-use.

### BR-004-4: First match wins, profile before global

Rules are evaluated in user order; the first match is used and evaluation stops. Profile
rules are evaluated before global rules. Order is the user's control surface, so it must be
honoured exactly and never reordered by specificity (FR-031).

### BR-004-5: Matching sources stay separate

Each matching source is matched against independently, never as one concatenated string.
This is what lets a pattern be anchored, keeps a class attribute from triggering a rule
intended for a name, allows a rule to be scoped to particular sources, and makes it possible
to report which source matched (ND-2, FR-067, FR-068, FR-069).

### BR-004-6: Label text is rendered text

A control's label contributes the text a user reads, never the markup that produces it, and
labels that wrap their control count equally with those referencing it by id
(ND-3, FR-029, FR-066).

### BR-004-7: The control's own constraints are a ceiling

A rule may narrow what the control declares; it may never widen it. Where a rule and the
control disagree, the stricter limit applies. A generated value that the page's own
validation would reject is a defect, not a rule the user chose (FR-012).

### BR-004-8: Interaction is simulated honestly

The event sequence matches what the control's kind would really produce — focus before
change, change before blur, and a click only for controls a user actually clicks. Announcing
a click on a text input is a lie the page may act on (ND-6, FR-013).

### BR-004-9: Generated values are never disclosed

No generated value — passwords above all — is written to a console, to storage, or to any
destination other than its target control. The reference logs generated passwords into the
page's console (ND-5, FR-026).

### BR-004-10: Descriptors carry identity, never content

A descriptor states what a control *is*, never what it currently holds. Nothing needs a
field's existing value to choose a generator, and not collecting it is what keeps the
privacy claim structural rather than promised (NFR-030).

### BR-004-11: One field's failure is one field's failure

Every field is generated and applied in isolation. A malformed pattern, an unsatisfiable
constraint or a hostile page cannot end the run (FR-010). The reference lets a single throw
abandon the remainder of the page (ND-10 / D10).

### BR-004-12: Identity resolution stays within one tree scope

A control's identity is resolved within the tree it lives in. A reference to a labelling
element is looked up in that same root, not in the top-level document, because an identifier
inside a shadow root is scoped to that root and looking it up globally would find an
unrelated element or nothing at all.

### BR-004-13: Globally disabled sources bound every rule

A rule scoped to a matching source the user has globally disabled does not match on that
source. Global settings are an upper bound on what any individual rule can reach, so turning
a noisy source off is a guarantee rather than a default that rules can quietly re-enable
(FR-028, FR-067).

### BR-004-14: Generation is seedable

Given a fixed seed and a fixed set of descriptors, generation produces identical values.
Randomness is a runtime default, not a property of the design — without this, the engine's
behaviour cannot be asserted in a test (NFR-012, NFR-013).

"A fixed set of descriptors" now includes their tokens, and a token is minted fresh for each
fill. So a seed alone reproduces the *persona*; reproducing a whole page's values needs the
descriptors that were sent, tokens included. That is what a test supplies and what a live fill
deliberately does not.

### BR-004-15: A control's value depends on the control, not on when it was asked

The value for a control is a function of the operation and that control's token. It does not
depend on the order controls were described in, on which batch they arrived in, or on how many
values were generated before it.

This is what makes it safe for the page to force a second write (FR-080). Drawing from one
running stream would give a control described again in a later pass the *next* value rather
than the same one — so an email refilled after the page wiped it would stop matching the
"confirm email" filled earlier, and UC-006 would be broken by the cascade itself, on exactly
the pages where it is hardest to notice.

It also means the answer is not remembered. Nothing stores what a control was given; the same
question is simply asked again and produces the same answer. A cache would be a place where
generated values live beyond the moment they are used, which BR-004-9 and NFR-031 both push
against.

The rule is scoped to one fill. Filling the same page again produces a new person and new
values (BR-004-3, FR-075).

### BR-004-16: A radio group's token is the group's, not a member's

A group is decided once and every member receives the same answer, so the answer is derived
from a token for the *group*. Deriving it from whichever member happened to be described first
would work only for as long as that member was the first one described — and a control revealed
by an earlier answer changes the order (UC-034 A2), which would silently give the group a
different answer on the pass after the page changed.

### BR-004-17: A confirmation field's value outranks a matching rule

Where a control confirms another (UC-006), it takes the confirmed control's value even when a
rule matches it. A confirmation field that does not equal what it confirms fails the page's own
validation, which is the only reason the field exists — so honouring the rule would produce a
form that cannot be submitted, out of deference to a preference the user expressed about
something else. The overridden rule is named in the field's provenance rather than dropped
silently, so the outcome is explicable (FR-024, FR-069).

This is the only place a rule is overruled by the engine rather than by the page. It is narrow
on purpose: the marker alone is not enough, the field must also resolve to a value there is
something to agree *with*. A control called `repeat_order_reference` confirms nothing the system
knows about, and a rule governs it normally.

### BR-004-18: A rule draws from the fill's persona unless it says otherwise

A rule whose generator names something the persona holds — a name, an email, a username, an
organisation, a telephone number, a URL — draws it from *this fill's* persona by default, so
writing a rule cannot accidentally break the coherence ND-1 exists to provide. A rule may opt
out per rule, in which case its value is derived from the control's own token and is internally
plausible but unrelated to the rest of the form.

The default matters more than the option does. A user writing a rule is thinking about one
field; the effect of breaking coherence shows up in a different field, usually the page's own
confirmation or summary, and is attributed to a bug rather than to the rule (FR-023).
