# Use Case: Edit a URL Profile

## Overview

**Use Case ID:** UC-015
**Use Case Name:** Edit a URL Profile
**Primary Actor:** Power User
**Goal:** Change a profile's name, the pages it applies to, or the rules in it
**Status:** Draft

Includes UC-024 (persist and propagate). Rule editing is UC-009..UC-013, unchanged.

**Traces to:** FR-046

## Preconditions

- The Power User has the settings open
- The profile exists

## Main Success Scenario

1. The Power User expands a profile. Its name, whether it is enabled, its address patterns and
   its rules are shown.
2. The Power User changes any of them.
3. The system stores each change as it is made (UC-024).
4. The system keeps the list header in agreement with what is being typed — the profile's name,
   and whether it is marked as matching nothing.
5. The next fill on a matching page uses the profile as changed, without a reload.

## Alternative Flows

### A1: The profile is turned off rather than deleted

**Trigger:** The Power User unticks Enabled (step 2)
**Flow:**

1. The profile is skipped during resolution, and the next matching profile — or the global
   rules alone — governs the page.
2. The profile and its rules are kept, so turning it back on restores exactly what was there.

### A2: The last address pattern is removed

**Trigger:** The Power User removes a profile's only pattern (step 2)
**Flow:**

1. The profile matches no page. It is marked in the list and states the problem inside it
   (UC-014 A2).
2. Its rules are kept.

### A3: Settings are changed somewhere else while a profile is open

**Trigger:** Another copy of the options page writes settings (UC-024)
**Flow:**

1. This page takes the other writer's state into memory so its next write does not revert them.
2. The profiles list is **not** re-rendered while a profile is expanded: replacing it would
   collapse the profile and discard the rule being written inside it.
3. A rule open inside the profile is carried across into the other writer's state.
4. The list catches up when the profile is closed.

### A4: The other writer deleted the profile being edited

**Trigger:** A3, where the profile no longer exists in the stored state
**Flow:**

1. The rule being written inside it is dropped along with it.
2. The profile is not resurrected. The list it belonged to is gone, and bringing a profile back
   because somebody had one of its rules open would undo a deletion nobody asked to undo.
3. The editor closes, and the system says that it did and why. This is the one place A3's
   "do not re-render while a profile is open" does not hold: the editor now edits nothing, so
   every keystroke would be silently discarded, and a control that swallows typing is a worse
   outcome than the collapse A3 avoids. The focus is placed in the profiles list rather than
   dropped, because the control it was in no longer exists.

### A5: The change cannot be stored

**Trigger:** Storage rejects the change (step 3) — see UC-024 A2
**Flow:**

1. The previous profile remains in force.
2. The system reports that the change did not take effect, and why.

## Postconditions

### Success Postconditions

- The profile is as the Power User left it, in the position they left it
- What the list header shows and what the profile contains agree
- The stored settings and what the user sees agree

### Failure Postconditions

- The previous profile remains in force
- No rule has been written into a list it does not belong to

## Business Rules

### BR-015-1: The header must follow the body, without rebuilding it

A profile's name and its "matches nothing" mark are shown in the collapsed header, and both are
derived from fields inside the expanded body. Rebuilding the row on each keystroke would take
the caret with it, so the header is updated in place instead.

Both parts, not one. The mark was missed when this was built and the failure was exactly the
control's purpose: a profile with no address patterns is marked as matching nothing, and typing
the pattern that fixed it left the mark standing. The one state the mark exists to report was
the one state in which it lied.

### BR-015-2: A rule is written to the list it was opened from

The rule editor operates on whichever list it was given — the global one, or one profile's.
Everything it holds outside the DOM has to agree: the draft carried across a foreign write, and
the undo offer, which is only valid against the list the rule was deleted from.

Restoring a deleted rule into a different list would put it at a position chosen for another
one; carrying a draft into the wrong list would create a duplicate global rule *and* lose the
profile edit, which is both halves of what the draft exists to prevent.

### BR-015-3: Turning a profile off is not deleting it

Disabled profiles are skipped during resolution and keep their rules. "Turn this one off while
I test something" is a thing users do constantly, and making them delete and rewrite a rule set
to do it would be the reference's carelessness with the user's work in a new place.
