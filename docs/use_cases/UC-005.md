# Use Case: Exclude a Field from Filling

## Overview

**Use Case ID:** UC-005
**Use Case Name:** Exclude a Field from Filling
**Primary Actor:** *(none — included subfunction of UC-001, UC-002, UC-003, UC-034)*
**Goal:** Decide, for one form control, whether it must be left untouched
**Status:** Draft

Included by UC-001, UC-002, UC-003 and UC-034. Runs in the page agent, before any value is
requested for a field, so that excluded fields never reach the generator.

Entered once per candidate **per pass**, not once per fill. A page that changes in response to
being filled changes what is excluded, so a decision made here is a statement about the pass
that made it and is never carried forward (UC-034 A2).

**Traces to:** FR-033, FR-034, FR-035, FR-036, FR-071, FR-079

## Preconditions

- The page agent is active in this frame and the domain is not excluded (UC-008)
- Current settings have been loaded, including the ignore patterns and the two exclusion
  toggles
- A candidate control has been located by the walk

## Main Success Scenario

1. The system receives one candidate control.
2. The system excludes the control if the Tester has interacted with it since the fill began,
   recording the reason as "user touched".
3. The system checks the control's kind and excludes it if it is a button, submit, reset,
   file, image or hidden control.
4. The system excludes the control if the page marks it unavailable for editing —
   disabled, read-only, or declared disabled to assistive technology.
5. The system builds the control's identity from the matching sources enabled in settings.
6. The system excludes the control if its identity matches any ignore pattern.
7. The system excludes the control if hidden-field exclusion is enabled and the control is
   not perceivable to a sighted user.
8. The system excludes the control if pre-filled exclusion is enabled and the control
   already holds a value.
9. The system reports the control as fillable and the fill proceeds.

## Alternative Flows

### A1: Control is a radio button in an already-answered group

**Trigger:** Pre-filled exclusion is enabled and the control is a radio button (step 8)
**Flow:**

1. The system takes the group to be every radio button sharing the control's name within the
   same form, or within the document where the control has no form.
2. The system excludes the whole group if any member is selected, applying A4 to decide
   whether a selection counts as user content.
3. Otherwise the use case continues at step 9.

### A2: Control is a checkbox

**Trigger:** Pre-filled exclusion is enabled and the control is a checkbox (step 8)
**Flow:**

1. The system does not treat checked state as pre-filled content.
2. The use case continues at step 9.

### A3: Control appears to be a honeypot

**Trigger:** Hidden-field exclusion is enabled and any of the following holds (step 7): the
browser reports the control as not visible; its rendered area is zero; its computed opacity
is zero; it is clipped away; it is positioned outside the document bounds; or it is marked
hidden to assistive technology and removed from the tab order
**Flow:**

1. The system treats the control as hidden and excludes it.
2. The system records the exclusion reason as "hidden" in the fill report.

This list is the definition, not examples of it. "Honeypot avoidance" without an enumerated
set becomes whatever the implementer judged on the day.

### A4: Control was written by an earlier fill on this same page

**Trigger:** Pre-filled exclusion is enabled and the control holds a value, or a selection,
that this extension wrote during an earlier fill of the current page (step 8, and step 2
of A1)
**Flow:**

1. The system does not treat that value as user content.
2. The use case continues at step 9, so the control is filled again with the new persona.

This covers an earlier *fill*. A control still holding what the current fill wrote is a
different case and never reaches this use case at all — see BR-005-9.

### A5: Ignore pattern is invalid, or would not finish

**Trigger:** A stored ignore pattern cannot be interpreted, or can be interpreted and would
backtrack catastrophically (step 6)
**Flow:**

1. The system skips that pattern and continues evaluating the remaining patterns.
2. The system records a settings warning once per fill, not once per field, and names the
   pattern in the fill report — an exclusion that did not run means a field the Tester asked to
   be left alone was filled, which is the part they may need to undo by hand.
3. The use case continues at step 7.

**A pattern that will not finish is skipped for the same reason as one that will not compile,
and the second half was missing until 2026-08-24.** The editor stores a half-typed pattern on
purpose — that is what makes this flow necessary rather than a failure — and an import stores one
out of a file and names it (UC-026 A8). Neither is a reason to *evaluate* it: the exclusion check
runs every stored pattern against every source of every control on every pass, and the sources
are the page's own. Measured against ordinary utility class strings, `^(\s*[\w-]+)+$` cost 287 ms
at 40 characters, 18.9 s at 50 and 55.7 s at 86 — for one call, on one control.

Note where those inputs sit against NFR-032, which asks for identity to be truncated to 1,024
characters: every one of them is an order of magnitude *under* that bound. Truncation is worth
having and would not have prevented any of it, because backtracking is exponential in length; the
cliff here is around 40 characters, which is shorter than a great many honest labels. So the
containment is not to bound the input but to decline the pattern, using the same `validateMatcher`
that draws the warning beside the field in the exclusion editor — and it happens in the
background, before the page is given the pattern at all.

### A6: Identity cannot be determined

**Trigger:** The control carries none of the enabled matching sources (step 5)
**Flow:**

1. The system treats the identity as empty.
2. Pattern-based exclusion cannot match, so the use case continues at step 7.

### A7: The Tester interacts with a control while the fill is running

**Trigger:** An input, key press or pointer interaction originating from the Tester rather than
from the extension reaches a control after the fill began (step 2) — see UC-034 A5
**Flow:**

1. The system excludes the control for the remainder of the operation, with the reason "user
   touched", and nothing is written to it.
2. The exclusion is not re-decided on a later pass. It is the one decision here that *is*
   carried forward, because the fact it records is about the Tester rather than about the page.

The discrimination is exact and free: every event the extension dispatches — including the
click a checkbox genuinely receives — is untrusted, because only the platform can mark an event
trusted. Nothing here depends on timing or on remembering to set a flag.

## Postconditions

### Success Postconditions

- The control is classified as either fillable or excluded — once per pass, and the answer may
  legitimately differ from the previous pass's
- An excluded control carries a single machine-readable reason, available to the fill report
- The reason reflects the state of the page now, not the state it was in when an earlier pass
  looked at it
- No control has been modified, and no event has been dispatched
- No value read from the control has been retained

### Failure Postconditions

- A control that cannot be classified is treated as **excluded**, never as fillable
- The failure is recorded against that control in the fill report
- The remaining controls in the run are unaffected

## Business Rules

### BR-005-1: Exclusion is fail-safe

When classification is uncertain or throws, the control is excluded. Filling a field that
should have been left alone is destructive and silent; skipping one is visible in the report
and recoverable by the user.

### BR-005-2: Checked state is not content

A checkbox's checked state is never "existing content" for the purposes of pre-filled
exclusion. An unchecked box is indistinguishable from an untouched one, so treating it as
content would make pre-filled exclusion disable all checkbox filling.

### BR-005-3: Radio groups are scoped to their form

A radio group is the set of radio buttons sharing a name **within the same form**, not within
the document. Two forms on one page may legitimately use the same group name; the reference
searches the whole document and lets them interfere (ND-5).

A radio button with no owning form has no such boundary available. Its group is then every
same-named radio in the document, which matches what the browser itself does when deciding
which buttons are mutually exclusive.

### BR-005-4: Exclusion precedes identification for cost, not for meaning

Cheap structural checks run before identity is built, purely to avoid the cost of building
identity for a control that is already excluded. The outcome must not depend on this ordering.

The saving is now worth more than it was. Since UC-034 this use case runs once per candidate
per **pass** rather than once per fill, so everything in it — including the perceivability
check, which is the expensive one, reaching for layout and computed style — is paid as many
times as the page cascades. The ordering is what keeps that multiplication off the controls
that were never going to be filled.

Re-running it is not optional and the cost is not a reason to weaken it. A control excluded as
`disabled` in pass 1 and enabled by pass 2 is the entire point of UC-034 A2, and it cannot be
noticed without asking again. Where the cost has to come down, it comes down by making the
check cheaper or by narrowing what is re-examined — never by remembering an answer, which is
the one thing that would make the re-run meaningless.

### BR-005-5: Hidden means not perceivable, not merely zero-sized

Zero width and height is one way to hide a control, not the definition. Full transparency,
off-screen positioning and clipping all count as hidden. This is what makes honeypot fields
safe (FR-071); the reference's size-and-visibility test misses all three (ND-16).

### BR-005-6: One reason per exclusion

When several rules would exclude the same control, the **first** to fire is the reported
reason, evaluated in the order of the main scenario. Users debugging a skipped field need one
answer, not a set.

### BR-005-7: Our own writes are not user content

A value this extension wrote during an earlier fill of the current page is never treated as
existing content by pre-filled exclusion. Without this, enabling "skip fields that already
have content" would silently disable the ability to fill the same page twice — two
reasonable settings cancelling each other out.

What is remembered is *which controls were written*, by element identity, for as long as the
page lives. No written or read value is retained, so NFR-010 holds unchanged.

### BR-005-8: Every exclusion is reportable

No control is ever silently skipped. Each exclusion contributes a reason to the fill report
(FR-009), which is what lets a user distinguish "nothing to fill" from "everything was
ignored".

### BR-005-9: A control the current fill already filled is not an exclusion

A control still holding a value this fill wrote is left alone, but it is **not** excluded and
gets no reason. It keeps the `filled` outcome it already earned, and this use case is never
entered for it again.

It is worth stating because the obvious implementation is the wrong one. Reaching this use case
with such a control and inventing a reason for it — "already filled by us" — would put an
exclusion in the report for a control that was filled, and the closest existing reason,
`pre-filled`, would be an outright lie about why it was left alone. The user would then be told
the extension skipped a field it in fact filled, which is the same class of dishonesty in the
report that write verification exists to remove.

### BR-005-10: The Tester's interaction is remembered; the page's state is not

Every decision in this use case is re-made from scratch on each pass, with one exception: a
control the Tester has touched stays excluded for the rest of the operation (FR-079).

The asymmetry is deliberate. Every other reason here is a statement about the page, and the
page is re-read each pass because it changes. "The Tester was working here" is a statement
about the Tester, and it does not stop being true because the page moved. Re-deciding it would
mean writing to a field somebody is typing into, which is the one failure in this design where
the user loses work rather than the fill being incomplete (BR-034-5).
