# Use Case: Fill the Current Form

## Overview

**Use Case ID:** UC-002
**Use Case Name:** Fill the Current Form
**Primary Actor:** Tester
**Goal:** Populate every fillable control belonging to the form the Tester is pointing at, and
nothing outside it
**Status:** Draft

Includes UC-004, UC-005 and UC-034. Extended by UC-008 (excluded domains).

**Traces to:** FR-002, FR-004, FR-005, FR-006, FR-009, FR-010 · **Design:** DD-008, ND-5

A page is often several forms: a search box in the header, a newsletter sign-up in the footer,
and the checkout the Tester is actually working on. Filling all of them to exercise one of them
is the behaviour this use case exists to avoid.

The hard part is not scoping to a `<form>`. It is that **most application forms are not
`<form>` elements at all** — a React checkout is a `<div>` — so "the current form" has to be
resolved from what the page does express. DD-008 is that resolution, and it is a ladder rather
than a heuristic precisely so that the answer is predictable: a scope the user cannot predict is
the same defect as a rule they cannot predict (ND-2).

## Preconditions

- The Tester is viewing a page the extension is permitted to act on, and that page's domain is
  not excluded (UC-008)
- The page agent is present in that page's frames
- Settings are loaded

## Main Success Scenario

1. The Tester invokes "fill the current form", from the context menu, a keyboard shortcut, or
   any other channel that offers the scope.
2. The system determines the **anchor**: the element the Tester pointed at.
3. The system resolves the anchor to a **form root** by the first rule that matches
   (BR-002-1), and records which rule decided it.
4. The system begins one fill operation over that root, and issues it with the settings in
   force.
5. The system collects every candidate control within the root, and no control outside it.
6. The system classifies each candidate as fillable or excluded (UC-005).
7. The system determines and applies a value for each fillable control (UC-004), following the
   page's own reaction until it settles or reaches a bound (UC-034).
8. The system reports the outcome, naming the scope as the form rather than the page (DD-006).

## Alternative Flows

*Ordered by the step whose failure or variation triggers them.*

### A1: The anchor is not the element the Tester clicked

**Trigger:** The scope was invoked by a keyboard shortcut, or from a menu opened over
something that is not a control (step 2)
**Flow:**

1. The system takes the currently focused element as the anchor.
2. Failing that, it takes the last control focused during this page's lifetime.
3. The use case continues at step 3.

**Why the third source exists:** tab through a form, click somewhere neutral, then use the
shortcut. It is the common way the scope is invoked from the keyboard, and without it the
Tester presses a key and watches nothing happen. It costs nothing to keep: element identity
only, never a value, exactly as the "written by us" set does (BR-005-7), so NFR-010 is
untouched.

**How the system knows this flow applies, added 2026-08-16.** The fill instruction carries the
trigger — menu, shortcut or toolbar — because the scope alone cannot distinguish them and the
agent has no other way to tell. Without it the agent guessed, and guessed by preferring the last
right-clicked element for as long as that element existed: a single right-click anywhere on a
page sent every later shortcut to the same place, for as long as the page stayed open. The flow
above was specified correctly and simply never ran. A trigger the agent does not recognise is
refused rather than guessed at, for the same reason.

**A right-click on blank page background is not the first source.** `<body>` is what such a click
reports, it is connected for the life of the page, and it is not something the Tester pointed
*at* — which is this flow's second trigger, "a menu opened over something that is not a control".

### A2: No anchor at all

**Trigger:** The Tester has not touched the page — a fresh load, invoked by shortcut (step 2)
**Flow:**

1. The system counts the form-like units in the page.
2. Exactly one: that unit is the root, and the use case continues at step 4.
3. None: the page is the root, and the use case continues at step 4.
4. Two or more: the page is the root, and the use case continues at step 4.

**Why widening is right here and wrong in A3:** see BR-002-2. No narrower intent was ever
stated, so nothing is being overridden — and refusing would again mean a keypress that does
nothing.

### A3: The anchor resolves to no form root

**Trigger:** Every rule in the ladder fails for an anchor the Tester did point at (step 3)
**Flow:**

1. The system fills nothing.
2. The system reports that it could not determine a form around the anchor, and says so in
   those terms rather than reporting an empty fill.

**Why it refuses rather than widening:** the Tester pointed at something. Filling the whole
page instead does what they explicitly did not ask for, and on a page whose other forms they
were avoiding, it is destructive (BR-002-2).

### A4: The form root contains no fillable control

**Trigger:** The root resolves, but every control in it is excluded or there are none
(step 6)
**Flow:**

1. The system reports zero controls filled, with the scope named and the exclusions counted.
2. This is a success, not a failure (BR-001-4), and must be distinguishable from one.

### A5: The anchor is inside a frame

**Trigger:** The Tester pointed at a control inside an iframe (step 2)
**Flow:**

1. The system resolves the form root **within that frame**, using that frame's own document.
2. Only that frame takes part in the fill; other frames are not asked.
3. The use case continues at step 4.

**Why only that frame:** the form the Tester pointed at cannot span a frame boundary — a
document is the outer limit of any root the ladder can return. Filling sibling frames would be
the page scope wearing the form scope's name.

### A6: The page changes the form while it is being filled

**Trigger:** Filling reveals or removes controls within the root (step 7)
**Flow:**

1. The system follows the cascade within the root, as UC-034 describes.
2. Controls revealed inside the root are filled; controls revealed outside it are not.

## Postconditions

### Success Postconditions

- Every fillable control within the resolved root holds a value, or is recorded with a reason
  for not holding one
- **No control outside the root has been read, written, or reported on**
- The result names the scope as a form, and which rule of the ladder resolved it
- All persona-derived values within the scope agree with one another
- No form has been submitted and no navigation has occurred

### Failure Postconditions

- Controls filled before the failure retain their values
- The result names the failure and its cause
- Where no root could be resolved, nothing was filled and the result says why

## Business Rules

### BR-002-1: The form root is resolved by a fixed ladder, not by a guess

From the anchor, the first rule that matches decides the root (DD-008):

| | Rule | Why |
|---|---|---|
| 1 | `element.form` | The page said so |
| 2 | Nearest ancestor `[role="form"]` or `<fieldset>` | The author said so, without a `<form>` tag |
| 3 | Nearest ancestor containing the anchor **and a submit control** | A form is the thing you can submit |
| 4 | *(anchored)* fill nothing and report why | An explicit narrowing must not be overridden |

Rule 1 is `element.form` and never `closest("form")`. HTML associates a control with a form by
the `form="id"` attribute as well as by containment, which is how a modal or a sticky footer
holds the submit button for fields outside it — `closest` gets those wrong in both directions.
Same class of correctness fix as `element.labels` over `label[for]` (ND-3).

Rule 3 is preferred over the more obvious "nearest container holding more than one field"
because it is both more accurate and explainable in one sentence: *the smallest block containing
the field you pointed at and its submit button*.

### BR-002-2: An anchored scope is never widened; an anchorless one may be

Where the Tester pointed at something and no root can be found, the fill refuses (A3). Where
they pointed at nothing, the scope widens to the page (A2).

This asymmetry is the design, not an inconsistency. Widening after an anchor overrides a
narrowing the Tester expressed on purpose. Widening with no anchor overrides nothing, because no
narrower intent was ever stated. Where two or more form-like units compete for an absent cursor,
the page is chosen over the largest unit, because a superset cannot be wrong about which one was
meant while a guess silently fails whenever the other was wanted.

### BR-002-3: The scope is a root, not a filter

The engine is given the resolved root to walk. It is not given the page and a test for
membership. This is ND-5's correction: the reference binds its walk to the global `document` and
then filters, so every control on the page is examined, and any defect in the membership test
leaks into a scope the user narrowed on purpose. A root that is walked cannot leak.

### BR-002-4: The result must say which scope ran, and which rule chose it

"6 filled" reads identically for a form and for a whole page, and DD-008 made the scope
inferable three ways. The result names the scope (DD-006), and the per-control report names the
ladder rule that resolved the root — because a Tester surprised by what was filled needs to know
*why the boundary fell where it did*, which is the same argument provenance makes for values
(FR-069).

### BR-002-5: The anchor is identity, never content

The three anchor sources record which element, never what it holds. Nothing about the anchor is
retained beyond the page's lifetime, and nothing about it is written to storage (NFR-010,
NFR-030).
