# Use Case: Fill All Inputs on the Page

## Overview

**Use Case ID:** UC-001
**Use Case Name:** Fill All Inputs on the Page
**Primary Actor:** Tester
**Goal:** Populate every fillable control on the current page, including its frames, in one
action
**Status:** Draft

Includes UC-004, UC-005 and UC-034. Extended by UC-008 (excluded domains).

**Traces to:** FR-001, FR-004, FR-005, FR-006, FR-007, FR-008, FR-009, FR-010, FR-075,
FR-076, FR-078, FR-079

## Preconditions

- The Tester is viewing a page the extension is permitted to act on
- The page agent is present in that page's frames
- Settings are loaded

## Main Success Scenario

1. The Tester invokes "fill all inputs".
2. The system identifies the current page and every frame within it that it can reach.
3. The system begins one fill operation covering all of those frames together, and issues it
   with the settings in force.
4. Each frame collects its candidate controls.
5. Each frame classifies every candidate as fillable or excluded (UC-005).
6. The system determines and applies a value for every fillable control across all frames
   (UC-004), drawing them all from a single persona.
7. Each frame follows the page's own reaction to being filled — options rewritten, fields
   revealed, controls enabled, values reverted — until it settles or reaches a declared bound
   (UC-034).
8. Each frame reports what it filled, skipped and failed, and whether it settled or was
   capped.
9. The system combines the frames' reports into one result for the operation.
10. The system indicates the outcome to the Tester.

## Alternative Flows

### A1: The page contains nothing fillable

**Trigger:** No frame yields a fillable control (step 5)
**Flow:**

1. The system reports that there was nothing to fill, distinguishing this from a failure.
2. The use case ends successfully.

### A2: Some frames cannot be reached

**Trigger:** A frame is sandboxed, or otherwise closed to the extension (step 2)
**Flow:**

1. The system fills the frames it can reach.
2. The system records the unreachable frames in the result.
3. The use case continues at step 9.

### A3: A frame fails during the fill

**Trigger:** A frame becomes unavailable, navigates away, or errors mid-operation (step 6)
**Flow:**

1. The system abandons that frame only, recording the cause.
2. Values already applied in that frame remain; nothing is rolled back.
3. The use case continues at step 8 for the remaining frames.

### A4: The page agent is not present

**Trigger:** The page loaded before the extension was installed or updated, or the page is
one the browser does not permit acting on (step 2)
**Flow:**

1. The system reports that this page cannot be filled, and why.
2. The system states whether reloading the page would resolve it.
3. The use case ends.

### A5: The domain is excluded

**Trigger:** The page's domain matches the user's exclusion list (step 2) — see UC-008
**Flow:**

1. The system performs no fill.
2. The system indicates that the domain is excluded, so the absence of a fill is not read as
   a fault.
3. The use case ends.

### A6: A frame appears after the fill has started

**Trigger:** A frame is added to the page — by a route change, or by lazy loading — after
step 2 enumerated the frames (step 6)
**Flow:**

1. The system does not fill the new frame; the operation covers the frames that existed when
   it began.
2. The use case ends normally for the frames it did cover.
3. The Tester may invoke another fill to cover the new frame, which will use a new persona.

### A7: A fill is already running

**Trigger:** The Tester invokes a fill while an operation on the same page is in progress
**Flow:**

1. The system ignores the new invocation.
2. The use case ends without starting a second operation.

An operation is in progress for as long as any frame is still resolving the page's own
reaction to being filled (UC-034), which on a cascading page is seconds rather than
milliseconds. The window in which this flow applies is therefore wide enough for a Tester to
enter it deliberately, believing the first invocation did nothing — so the second invocation
being ignored has to be visible rather than silent, which is DD-006's obligation to satisfy.

A Tester who instead starts *typing* is not invoking a fill: that ends the cascade and leaves
what they typed alone (UC-034 A5).

## Postconditions

### Success Postconditions

- Every fillable control across every reachable frame holds a value, or is recorded with a
  reason for not holding one
- A control is recorded as filled only where the value written to it was read back and found
  to have been accepted; one the page rejected or cleared is recorded as failed (FR-076)
- Every reachable frame has either settled — nothing left that a further pass could fill — or
  stopped at a declared bound and said so, with how many controls a further pass would have
  covered (UC-034, FR-078). A fill no longer ends when the first walk does
- All persona-derived values agree with one another across the whole page, frames included
- The result distinguishes filled, skipped-with-reason, failed-with-cause, and unreachable
- No form has been submitted and no navigation has occurred
- The persona and the generated values have been discarded, unless the user has asked for the persona to carry across fills (NFR-031)

### Failure Postconditions

- Controls filled before the failure retain their values
- The result names the failure and its cause
- The page is left in a usable state — no control is partially written, and no fill remains
  in progress

## Business Rules

### BR-001-1: One page, one persona — frames included

A page and its frames are one fill and share one persona. A checkout whose card fields sit in
a payment iframe must receive the same person's name as the billing fields in the parent
document. Treating each frame as its own fill would reintroduce exactly the incoherence ND-1
exists to remove, in the case where it is most visible.

Frames cannot communicate with one another, so this works only because the persona exists
before any frame is asked for anything (BR-004-1a). Each frame reports independently and
receives values drawn from a person already created for the operation. No frame's *filling*
waits for another's.

The *result* does wait, and since UC-034 it has to. A frame's duration now depends on how much
its own page cascades, so two frames in one tab can finish seconds apart — and a result
assembled before the slower one reported would be short by that frame's whole account, with
nothing to say so. Every frame therefore announces that it is taking part, and the result is
assembled once each of them has had its say or has been silent long enough to be treated as
gone.

### BR-001-2: A fill never submits

The system writes values and dispatches the interactions a user would produce, and stops
there. It never activates a submit control and never causes navigation. Anything else would
make the extension unsafe to invoke on a page the user has not finished reading.

### BR-001-3: Every invocation produces a new person by default

Filling the same page twice yields two unrelated personas, and the second fill overwrites the
first — including when the user has chosen to skip pre-filled fields, because values this
extension wrote are not user content (BR-005-7). Repeated submission with fresh data is a
primary reason testers use this tool (FR-075).

"By default" is deliberate: BR-004-3 reserves the possibility of a user carrying one persona
across fills for multi-step forms. This use case must not assume the persona it receives is
freshly minted.

### BR-001-4: Nothing to fill is a success, not a failure

A page with no fillable controls is a valid outcome and must be reported as such. Conflating
it with failure is what makes the reference's silence ambiguous — the user cannot tell an
empty page from a broken extension from an excluded domain.

### BR-001-5: One frame's failure is one frame's failure

Frames are filled independently. An unreachable, hostile or navigating frame cannot prevent
the rest of the page being filled, and cannot discard the results already obtained (FR-010).

### BR-001-6: A channel may offer fewer scopes, but never a different behaviour

The three scopes — page, form, control — are UC-001, UC-002 and UC-003. A trigger channel
chooses which of them it can reach, and nothing else: where two channels invoke the same
scope, the results are identical.

The toolbar button reaches only this use case, because it has no cursor position to derive a
narrower scope from. The context menu and the keyboard commands reach all three.

### BR-001-7: The result is always available, whether or not it is shown

Every fill produces a complete structured result even when the interface displays only a
summary or nothing at all. What the user is shown is a presentation decision (DD-006); that
the result exists is not (FR-009).
