# Use Case: Persist and Propagate Settings

## Overview

**Use Case ID:** UC-024
**Use Case Name:** Persist and Propagate Settings
**Primary Actor:** *(none — included subfunction of every configuration use case)*
**Goal:** Store a settings change durably and bring every running part of the extension into
agreement with it, without requiring a reload
**Status:** Draft

Included by UC-009..UC-012, UC-014..UC-016, UC-018..UC-023, UC-026, UC-027, UC-028.
Extended by UC-029 (sync).

**Traces to:** FR-051, NFR-021, NFR-023, NFR-025, NFR-026

## Preconditions

- A configuration use case has produced a complete, candidate settings state
- The candidate has been validated by the surface that produced it

## Main Success Scenario

1. The system receives the candidate settings state in full.
2. The system validates it against the settings schema, including every rule pattern and
   template.
3. The system writes the candidate to durable storage as a single replacement.
4. The system replaces its in-memory settings with the stored state and recompiles the rule
   patterns once.
5. The system reconciles the browser state derived from settings — the presence of the
   context menu.
6. The system confirms the change to the surface that requested it.

**There is no step that pushes settings to open tabs, and that is the design rather than an
omission (BR-024-6).** Every fill instruction carries the settings it should be filled with, so
a page agent is never asked to hold a copy that could go stale. FR-051's "takes effect in open
tabs without reloading them" is satisfied by there being nothing in the tab to update.

## Alternative Flows

### A1: A tab hosts no page agent

**Trigger:** A browser-internal page, an extension gallery page, or a page that loaded before
installation
**Flow:**

1. Nothing is required of this use case: no settings are sent to tabs at all (BR-024-6).
2. Such a tab announces itself when a fill is attempted on it, which is UC-001 A4's concern
   rather than this one.

### A2: The write fails

**Trigger:** Durable storage rejects the write, or is unavailable (step 3)
**Flow:**

1. The system abandons the change.
2. The previously stored settings remain in force, in storage and in memory alike.
3. The system reports the failure and its cause to the requesting surface.
4. The use case ends without propagating anything.

### A3: Stored size exceeds the available quota

**Trigger:** The candidate is larger than storage will accept (step 3)
**Flow:**

1. The system reports which quota was exceeded and by how much.
2. The use case continues as A2 from step 2 — the previous settings stand.

### A4: Validation rejects the candidate

**Trigger:** The candidate fails schema validation, or a pattern will not compile (step 2)
**Flow:**

1. The system reports which part of the candidate is invalid.
2. Nothing is written and nothing is propagated.
3. The use case ends.

### A5: Changes arrive faster than they can be stored

**Trigger:** Successive changes occur within the debounce interval (step 3)
**Flow:**

1. The system coalesces them, retaining the latest candidate.
2. The system performs one write for the coalesced result.
3. The use case continues at step 4.

### A6: The background context restarts

**Trigger:** The background context is evicted after the write
**Flow:**

1. On its next start the system reads the stored settings, which already reflect the change.
2. Nothing was held anywhere else, so nothing is stale — the restart costs a storage read and
   a pattern compilation, and no correctness.

## Postconditions

### Success Postconditions

- Storage holds exactly the candidate state, with no element of the previous state surviving
- The in-memory settings and the compiled patterns match what is stored
- Context menu presence reflects the stored state
- No page agent holds any settings at all between fills, so none can be stale
- No open tab required a reload, and none was messaged

### Failure Postconditions

- Storage holds the previous settings, complete and self-consistent
- The in-memory settings still match storage
- No page agent has received the rejected candidate — none receives settings outside a fill
- The requesting surface has been told the change did not take effect, and why

## Business Rules

### BR-024-1: Settings are replaced whole, never patched

A save writes a complete settings state. Partial updates admit the possibility of storage
holding a combination that no validation ever saw, which is the failure mode NFR-021 exists
to prevent.

### BR-024-2: A failed write changes nothing

If storage rejects the write, the previous configuration remains in force everywhere. The
system never ends up with memory and storage disagreeing, and never leaves the user with a
configuration they did not author.

### BR-024-3: Storage is the source of truth; memory is derived

The in-memory settings and the compiled patterns are a cache. They are populated from
storage and refreshed on write, never written to independently. On any doubt — a restart, an
external change — storage wins (ND-17, NFR-026).

**The options page is the exception that proves it, and it costs care.** That page holds the
whole state for its lifetime and writes all of it on every change, so its copy going stale is
not a display problem: the next write reverts whatever the other writer did, silently. It
therefore adopts foreign changes as they arrive. While a rule is open it adopts them *into
memory only* and leaves the rendered list alone — replacing the list would take the caret out
of the editor and discard a rule that has never validated, which lives nowhere else — and the
rule being edited is carried across into the adopted state so that the next write rebases onto
the other writer rather than over them. The screen catches up when the rule closes.

"While a rule is open" is a question the page asks on every foreign change, so the answer has
to become *no* when the editor goes away. It does not go away only by being closed: a profile's
rules are drawn inside the profile, so collapsing or deleting the profile destroys that editor
too, and a rule left open over it would answer yes for the rest of the session — the rule list
would then never re-render again on a foreign change, and every adoption would carry a draft
nobody could see (UC-015 A6). Carrying it also means knowing *which* list it belongs to, which
is fixed when the rule is opened rather than by whichever list was drawn most recently
(BR-015-2).

Adopting into memory also leaves the screen holding stale *positions*, which BR-024-10 answers.

Recognising a foreign change means recognising this page's *own* writes first, and those do not
come back as they were sent: `saveSettings` normalises the candidate through `parseSettings` and
stores the result (BR-024-7). Memory holds the un-normalised state, so a naive comparison called
every reshaping the parser did — a half-written rule dropped, a bound clamped, a key emitted in
a different order — somebody else's write. Adding a rule triggered it every time, because a new
rule has an empty pattern and the parser drops it. Both sides are put through the parser before
they are compared, so the question asked is the one that matters: does storage hold something
this page did not put there?

### BR-024-4: Each context receives only the settings it needs

A page agent is sent the exclusion toggles, ignore patterns, matching sources and domain
exclusions it must apply itself. It is not sent the rule list, the generator configuration or
the profiles, because it never uses them. Less crosses the boundary, and less is exposed if
a page ever compromises the agent.

### BR-024-5: Propagation is an optimisation, not a correctness requirement

A fill is always initiated by the background, which passes current settings along with the
instruction to fill. A page agent that missed a settings broadcast therefore still fills
correctly. Propagation exists so that page-load-time behaviour — domain exclusion and the
profile badge — is current, not so that filling is correct.

### BR-024-8: Patterns compile once per settings change

Rule and exclusion patterns are compiled when settings change, never per field or per fill.
Compiling 100 patterns against 500 fields on every run is 50,000 compilations the design
should not perform (ND-15, NFR-025).

### BR-024-9: Writes are coalesced

Continuous editing must not produce one write per keystroke. Changes are debounced so that
storage write-rate limits are never approached, which matters most for the synchronised
storage UC-029 introduces (NFR-023).

### BR-024-6: Settings travel with the work, not ahead of it

An agent is given the settings for the fill it is about to perform, in the same message that
asks for the fill (BR-024-4). It holds none between fills.

This is why live propagation needs no propagation. The obvious design — push every change to
every tab — has a failure mode this one cannot have: a tab that was asleep, throttled, or
mid-navigation misses the push and then fills with settings the user changed ten minutes ago,
silently and only sometimes. Sending settings with the request makes "which settings did this
fill use" answerable by looking at one message.

It also keeps the agent's resting footprint at nothing, which is what NFR-003's budget is for:
the alternative is every frame of every page holding a copy of the user's configuration.

### BR-024-7: A write is validated by the same reader that will load it

The candidate is put through the parser that reads settings back before it is written, and what
that parser returns is what gets stored. A state that survives the write but not the read is
the defect this removes — the user sees their rule saved, and it is gone or altered on the next
fill with nothing to indicate why.

**"Validated" here means *shape*, and only shape.** The parser coerces a stored state into the
current type: it drops what it cannot recognise, drops a rule with no pattern, and repairs some
values rather than rejecting them — it reorders a number generator's bounds if they are the
wrong way round, and clamps decimals and word counts into range. What it does *not* do is apply
FR-070. A rule whose regex will not compile, or whose template names a token that does not
exist, is well-shaped and survives the parser intact.

So "nothing invalid is written" (UC-009 A1, BR-009-1) does not rest on this rule. It rests on
the editor: `update` commits only when `validateRule` returns no problems, and the one path that
commits without asking — adding a rule — writes a rule with an empty pattern, which the parser
happens to drop. That is a composition of two separate guarantees rather than one, and it holds
today because the editor is the only writer.

**Recorded rather than closed, deliberately.** Filtering every write through `validateRule`
would make the invariant structural, and was considered on 2026-08-17. It was not taken: a rule
written by an earlier version that a later, stricter `validateRule` rejects would then vanish on
the next unrelated save, silently, which is the same shape as the DD-005 risk this project
already treats as its worst — user work discarded by a repair nobody asked for. The cheaper
guard is the one this note is: a future writer that is not the editor must validate, and now has
somewhere that says so.

### BR-024-10: Rows addressed by position check the position before writing

Every list of plain values the options page edits — domain exclusions, field exclusions, a
profile's address patterns — carries no identifiers, deliberately: two identical patterns are a
redundant configuration rather than an illegal one, and removing "the entry equal to this" would
take the first of them however far down the list the user clicked. So a row can only say *where*
its entry is.

That is sound while the section is on screen unchanged, and BR-024-3 is the reason it sometimes
is not. A section skipped for holding the focus, or for holding an open profile, keeps handlers
aimed at positions the adopted state has already moved — and it is skipped precisely because
someone is working in it. The next keystroke then edits somebody else's entry, the next delete
removes somebody else's entry, and a position past the end writes nothing at all while the box
on screen goes on showing what was typed.

Each such row therefore checks that its position still holds what the row was drawn from, and
what the row has written since, before it writes anything. When it does not, nothing is stored
and the section is redrawn with the change announced. That costs a keystroke and the caret,
which is the lesser fault by some distance: editing or deleting an entry the user never looked
at is worse, and a box showing text that was never stored is worse than both — the same
reasoning A2 applies to a rejected write.

Lists whose entries *do* carry identifiers — rules, profiles — are resolved by id rather than
guarded, which is this rule with a better instrument available.
