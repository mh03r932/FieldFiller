# Use Case: Synchronise Settings Across Devices

## Overview

**Use Case ID:** UC-029
**Use Case Name:** Synchronise Settings Across Devices
**Primary Actor:** Power User
**Goal:** The same configuration on every browser signed into the same account, with no
account of ours — the browser's own synchronised storage, opted into per device
**Status:** Draft

Extends UC-024: every write this use case makes or applies goes through the single-replacement
path that use case defines, and the sharded layout below changes how sections are *stored*,
not what they are. Inherits DD-002 resolved — the layout, the ceiling and the conflict
semantics are decided there and restated here only where the user must be able to read them.

**Traces to:** FR-058, FR-059 · NFR-022, NFR-023 · DD-002

## Preconditions

- The Power User has the settings open
- More than one browser is signed into the same browser account — aspirationally: the
  extension cannot observe this (A4), so it is not a precondition the system verifies

## Main Success Scenario

1. The Power User turns synchronisation on. It is off by default, and the choice is made
   separately on each device (BR-029-1).
2. The system looks at what the synchronised store holds.
3. Where it holds a usable configuration, the system shows both sides — what this device has,
   what the store has, in the same sentence — and the Power User chooses which becomes the
   configuration. Where it holds nothing usable, the local configuration seeds the store.
4. The system writes the configuration through to the synchronised store in the layout DD-002
   chose: rules and profiles sharded eight to a key, every other section a key of its own.
5. From then on, a settings change made anywhere arrives everywhere: a local change is
   written through on this device within the write-rate bound (BR-029-4), and a change from
   another device is applied here as a single replacement through UC-024's path.
6. The sync section of the settings screen carries two standing sentences, in plain terms:
   synchronisation stops carrying the configuration at roughly 399 rules and says so rather
   than truncating; when two devices change settings in the same window, the later write wins
   and discards up to eight rules (BR-029-3).

## Alternative Flows

### A1: The configuration outgrows what the store will carry

**Trigger:** The synchronised store rejects the write — its total quota, at roughly 399 rules
(step 5)
**Flow:**

1. Nothing is truncated (BR-029-5). Local storage keeps the whole configuration and remains
   the one that fills with.
2. The system marks the synchronised state as not current, so no device applies a thin copy
   as though it were whole.
3. The settings screen says synchronisation has stopped, what stopped it — the rule count
   against the store's capacity — and what restores it: removing rules, or turning
   synchronisation off and keeping the configuration local (NFR-022's degrade rather than
   fail).

**Why the mark exists.** A partial carry is not a stale configuration; it is a *different*
one. A device that applies 350 of 420 rules fills pages differently from the device that
holds 420, and no count on either screen would say why. The mark makes "this is not the
configuration" a fact the system states rather than an inconsistency the user diagnoses.

### A2: Two devices change settings in the same window

**Trigger:** A shard written by one device is overwritten by another before the first
arrives (step 5)
**Flow:**

1. The later write wins the shard. Up to eight rules of the earlier write are discarded.
2. Nothing detects or repairs this. It is accepted (DD-002), and the standing sentence on the
   sync screen said so before the user ever turned the feature on.

**Known limitation, recorded 2026-08-28 rather than discovered later: a discard can
reach further than one shard.** A device pushes a delta computed against the store *as it
is now*, not against the state it last agreed with — so a device holding a stale baseline
sends back differences it never made. Two forms:

1. *The echo*, which is **closed**. Adopting an arrival writes local settings, which used
   to mark a push pending over a configuration the device had just been given; a third
   device writing between the read that fed the adoption and that echo made the echo's
   delta non-empty, and what it wrote was a revert. `hasUnsentChange` now answers this at
   the source — local matching `agreed` means there is nothing to send, by definition.
2. *The stale edit*, which is **not closed**. An edit made on top of a baseline that has
   since moved still pushes a delta covering both the edit and whatever else has changed,
   so it can revert another device's concurrent write with a reach set by how far the two
   configurations differ rather than by the shard size. The window is narrow — the time
   between one device's read and its next write — and the loser then adopts the revert
   without noticing, because its own fingerprint check passes: its edit *was* pushed.

**Closing it needs a generation per key and a compare-and-set**, checked before adopting
and before pushing, which is a change to the layout rather than to any single decision.
Deferred rather than dismissed, and named here because the standing sentence in BR-029-3
promises "up to eight rules" — which is what the design intends and what the shard size was
measured for, and which this case can exceed. **The wording of that sentence is therefore an
open question**, not a settled one: it can stay as the description of the designed behaviour
with this exception documented, or it can be softened. It should not be left to be decided by
whoever next reads the discrepancy.

**Why no merge, and no apology beyond the sentence.** Merging two rule lists is choosing an
order nobody chose, and precedence is behaviour (FR-031) — the same argument BR-026-1 makes
against import merges, now inside a store the user cannot inspect. The shard size is what
keeps what has to be said small: eight rules, not the whole configuration, which is what the
reference's single-key layout would discard.

### A3: A change arrives while a rule is open in the editor

**Trigger:** A remote change lands on a device whose options page holds an open rule
(step 5)
**Flow:**

1. UC-024's adoption rules govern unchanged: the change is adopted into memory, the rendered
   list is left alone so the caret and the unvalidated draft survive, and the screen catches
   up when the rule closes (BR-024-3).

A synchronised configuration makes that rule's subject — a foreign writer — routine rather
than exceptional. The adoption path existed for two options pages; this use case is its
promotion to normal operation.

### A4: The browser's own synchronisation is signed out or broken

**Trigger:** Writes to the synchronised store succeed locally while nothing carries them
(step 5)
**Flow:**

1. Nothing is required of this use case, and nothing is claimed. The screen reports what was
   written and what was refused — never that another device is up to date.

**The platform exposes no way to know, and the screen does not pretend otherwise.** This is
the fourth requirement whose honest form is narrower than its written form, after FR-047,
FR-074 and FR-048: FR-058's "consistent everywhere" is a state of the user's browser account
that no extension API reports. What the extension *can* promise — written through, or refused
and said — is what the screen says, which is also everything FR-059 needs to be true.

### A5: The Power User turns synchronisation off

**Trigger:** The toggle is switched off (step 1, any later time)
**Flow:**

1. Local storage stays authoritative and complete; the replica stops being written to.
2. The copy in the synchronised store is left exactly as it is. Turning the feature off on
   one device must not reach into another device's configuration, and clearing the store
   would.

### A6: Shards arrive from a newer schema version

**Trigger:** Another device runs a newer build of the extension and has written shards this
build's schema does not fully name (step 5)
**Flow:**

1. They are read the way any stored state is read: through the tolerant parser, keeping what
   it recognises and defaulting the rest (DD-005).
2. Entries it cannot keep are dropped as they would be from local storage. The newer device
   still holds them; this one does not pretend to.

**Named here because synchronisation makes DD-005's accepted cost more likely to be paid.**
Mixed-version fleets are normal — an updated laptop beside an unupdated desktop — and sync is
the one source of foreign configuration states that cannot be refused at a boundary the way
UC-026 A2 refuses a newer file: it arrives. The migration ladder FR-073 asks for is the
remedy, and this flow is the standing argument for building it before any structural schema
change ships.

## Postconditions

### Success Postconditions

- The synchronised store holds the configuration in the sharded layout, or is marked not
  current — there is no third state
- Local storage holds the whole configuration, complete and valid, in every case
- A settings change on any device with the feature on is written through within the
  write-rate bound, or its failure is stated on the screen that made it
- The two standing sentences are on the sync screen, permanently

### Failure Postconditions

- Local storage holds the whole configuration, complete and valid — this use case has no
  failure postcondition in which it does not
- The synchronised state is marked not current rather than left silently partial
- The settings screen says synchronisation has stopped and what will restore it

## Business Rules

### BR-029-1: Opt-in, per device, off by default — and the toggle itself never syncs

The extension's stated posture is that settings stay on the device. Using the browser's
synchronised store is the user's decision, made on each device, and the flag is stored
locally and deliberately excluded from what is carried — a toggle that travelled would turn
synchronisation off everywhere the moment one device opted out, which is the single-key
conflict (A2) wearing a settings-screen face. There is no account of ours anywhere in the
feature (FR-058); the browser account is the user's existing trust relationship. What changes
is the privacy claim's shape — "stored on the device" becomes "stored on the device and,
where you have turned it on, in your browser's own synchronisation" — and the privacy surface
and changelog must say so in those terms when this ships, not after somebody asks.

### BR-029-2: Local storage is the store; the synchronised store is a replica

Every read that fills with settings comes from local storage. A remote change becomes local
through the same single-replacement write every other settings change uses (BR-024-1,
BR-024-3), never by reading the replica mid-operation. The system's own writes coming back as
arrivals are recognised the way the options page recognises a foreign writer (BR-024-3): both
sides compared after the parser, so the question asked is the one that matters — did the
store change, or did this device's own write return.

### BR-029-3: The two sentences are standing text, not acknowledgements

Synchronisation stops at roughly 399 rules; a conflict discards up to eight rules. Both are
permanent text on the sync screen, in those terms, because both describe the feature's normal
operation rather than an error state — the ceiling is where FR-044's unlimited set meets a
finite store, and the discard is what last-writer-wins means at this shard size. DD-002 left
these as obligations on this spec in those words: neither is a limitation to apologise for
in passing, and neither may live in a dialogue the user clicks through once. FR-059 is
load-bearing on the first sentence; the second is what makes A2 honest when it happens.

### BR-029-4: Written through at its own pace

Local writes keep the responsiveness they have today; the replica trails them. Synchronised
writes ride their own coalescing with NFR-023's bound — no more than 100 write operations per
hour under continuous editing — which the DD-002 measurement made cheap to honour: an
operation is counted per call, not per key, so a sharded save of twenty-odd keys is one of
them. The bound is a product decision rather than a platform limit, and it is stated as a
bound for that reason: the interval that satisfies it is implementation's to choose.

### BR-029-5: No truncation, ever

When the configuration no longer fits, synchronisation stops and says so (FR-059); it never
carries a prefix of the rule list silently. The not-current mark is the other half of the
rule: it is what stops a device from applying a partial copy as the whole, which is the one
outcome worse than not synchronising (A1).

### BR-029-6: The screen claims only what the extension can observe

Written, refused, stopped. Not "synced", not "your devices are up to date" — the platform
reports no such fact (A4), and a screen that asserted it would be FR-059's exact failure mode
inverted: confidence where the user needed truth. This is the same discipline the fill report
already holds (FR-009), applied to a smaller surface.
